工作流控制台扩展与批量任务操作实施方案

为页面查看增加真正的服务端分页，并在工作流任务页加入多选、批量重置和串行批量运行。

日期：2026-07-14　范围：Agent Bridge 后端 API、SQLite 查询、Capabilities Vue 前端

目标：页面不再被 30/50/200 条的单次拉取上限截断；MCP 的 artifacts_search 继续保持现有 limit 语义；工作流任务支持勾选多个任务后一次操作，其中批量运行严格等待前一个 run 进入终态后再开始下一个。

一、现状与根因

问题当前行为根因修改方向
工作流详情页产物 请求固定 limit: 30，没有分页控件。 WorkflowView.vue:384-392 直接截断；后端搜索 SQL 只有 LIMIT。 HTTP 产物接口增加 offset 和 total，前端使用服务端分页；MCP 调用不改变。
Agent 运行 页面请求最多 200 条，然后只在这批数据上客户端分页和搜索。 后端仓储已经有 offset，但页面没有使用；列表响应没有总数，搜索字段在前端过滤。 增加分页响应和服务端全文过滤；保留旧数组响应以降低外部兼容风险。
调用日志 页面请求最多 200 条，然后只在这批数据上客户端分页和搜索。 后端仓储已有 LIMIT ? OFFSET ?，但没有 count 查询；前端仍一次性拉 200 条。 增加服务端分页、总数、搜索条件和状态统计。
工作流任务批量操作 每行只有单任务“执行”和“重置”按钮。 前后端接口都按一个 task_key + task_version 处理。 前端增加跨客户端分页的选择状态，复用单任务接口顺序调用；批量运行等待每个 run 终态。

二、接口契约设计

2.1 产物页面接口

保留当前返回的 items，HTTP 接口增加分页字段。因为当前接口本身已经返回对象，增加字段不会破坏现有读取 result.items 的调用。

GET /workflow-artifacts?workflow_key=...&limit=50&offset=0

{
  "items": [...],
  "total": 137,
  "limit": 50,
  "offset": 0
}
  • 后端继续把单次页面请求限制在最多 50 条；页面通过 offset 请求下一页。
  • total 必须使用与列表完全相同的过滤条件：profile、workflow、query、path、task、run、tags、format、include_history。
  • 仓储查询保持稳定排序：updated_at DESC, id DESC。
  • MCP 的 artifacts_search 仍调用服务方法的非分页模式，默认/最大 limit 不变，不暴露页面分页字段作为 MCP 需求。

2.2 Agent 运行与调用日志接口

为避免把现有数组响应改成对象导致其他调用方破坏，增加可选的 paginated=true。不带该参数时继续返回旧数组；页面专用请求使用分页模式。

GET /agent-runs?paginated=true&limit=50&offset=0&search=workflow
GET /tool-call-logs?paginated=true&limit=100&offset=0&search=database

{
  "items": [...],
  "total": 1234,
  "limit": 50,
  "offset": 0,
  "counts": { "all": 1234, "success": 1100, "failed": 120, "running": 14 }
}
  • Agent 运行的 search 覆盖当前页面已有的 agent_name、profile_key、workflow_key、error，并补充 run_key/status。
  • 调用日志的 search 覆盖当前页面已有的 tool_name、actor、entrypoint、source_type、source_key。
  • counts 以相同日期/搜索/来源等基础过滤为准，但不受当前状态 tab 的单项筛选影响，从而保持 tab 数字完整。
  • 仓储增加与列表过滤完全一致的 COUNT(*) 查询；列表和 count 共用过滤条件构造逻辑，避免两套条件漂移。
  • 原有 limit、offset 的非分页数组调用保持可用；现有工作流进度页按 run_id 查询的少量调用无需改成分页。

for (const task of queue) {
  if (!canExecuteTask(task)) {
    skipped.push(task)
    continue
  }
  const started = await api.executeWorkflowTask(
    task.workflow_key, task.task_key, task.task_version || undefined,
  )
  if (!started.run_id) {
    failed.push({ task, reason: '未返回 run_id' })
    continue
  }
  const run = await waitForWorkflowRun(started.run_id)
  results.push({ task, run })
}
□ 不一次给全部任务设置 priority；priority 是一次性标记，每次只处理当前任务。
□ 单项 failed/no_task/stopped 记录结果后继续；网络错误或 workflow 已被其他运行占用时停止队列并保留未执行项。
□ 队列运行期间禁用同一工作流的单任务执行/重置，显示“第 x/y 个任务”；完成后刷新任务、运行记录和可见产物。
□ 单个任务执行仍保持现有行为：成功启动后进入 progress 页面。

四、关键取舍

批量运行的生命周期：批量运行只在当前页面内维护队列，不新增后台 batch 表、worker 或持久化状态。页面关闭后队列停止是预期行为；重新打开页面时，用户可以重新选择任务。页面仍会等待每个 workflow run 进入终态后再开始下一个，避免触发现有 workflow 级并发锁。
  • 不把 MCP 的 limit 上限改成页面所需的无限量，避免 agent 检索返回过多正文、增加上下文成本。
  • 不继续把所有记录拉到浏览器后再分页；total、search、status counts 都在 SQLite 侧完成。
  • 不把当前任务页改成服务端分页，因为任务列表目前没有 200 条截断问题；先保持其客户端筛选/分页，批量选择 key 设计为跨页可用。
  • Offset 分页适合当前管理页；列表排序必须保留时间加数据库 id 的稳定 tie-breaker。若未来需要在高频写入下无重复/无遗漏地连续导出，再升级为 cursor 分页。

五、验收标准

  1. 工作流详情页可以浏览超过 30 条当前产物，页面显示服务端 total，翻页后不会只在首批数据中切片。
  2. Agent 运行和调用日志超过 200 条时可以翻页访问全部保留期内数据；搜索和状态/日期筛选作用于全量匹配集。
  3. MCP artifacts_search 的默认行为、返回字段和 limit 上限不变。
  4. 任务页可以跨当前客户端分页勾选多个任务，一次批量重置。
  5. 批量运行严格按任务顺序执行，前一个 workflow run 未进入终态时不会提交下一个 execute 请求。
  6. 批量运行中发生单项失败时有明确结果汇总；发生外部并发冲突或网络错误时停止并保留未执行项，避免静默丢任务。
