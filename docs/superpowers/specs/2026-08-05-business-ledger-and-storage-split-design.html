业务台账与存储分库设计

为 Agent Bridge 增加由用户维护、受能力平面约束、可由 Agent 查询的轻量业务数据能力；同时将主业务、运行日志与业务台账数据拆分为独立 SQLite 文件。

已确认设计2026-08-05范围：台账能力、MCP、三库迁移

1. 决策摘要

产品名称：业务台账

面向 Excel 维护的业务资产、系统、应用、规则等数据。技术实体保留 ledger/dataset，不混同 MySQL、Hive 等外部通用数据库。

持久化 + 内存快照

SQLite 是唯一持久化来源；服务启动后异步构建每个台账的只读数据帧快照，浏览和 MCP 查询均只读内存。

一个顶级查询工具

对 Agent 直接暴露 query_business_ledger，不再要求 service/tool_name/params 包装，也不暴露台账管理操作。

已确认边界：不设草稿状态；字段类型支持文本、数字、枚举、日期、日期时间，不提供布尔类型；一期不使用 FTS；定义完整版本化，记录不保存逐条历史版本。

2. 目标与非目标

目标非目标
让管理员维护中小规模的自定义业务台账，并按字段定义进行受控查询。替代 MySQL、Hive、OLAP 或提供任意 SQL 查询。
让不同能力平面只能发现和查询其被授予的台账。按记录或字段配置独立的 Profile 权限。授权粒度一期是台账；字段是否可返回由定义控制。
支持 Excel 为主的批量维护、预览、导入和导出。实现多维表格、公式、协同编辑、视图编排或实时多人冲突解决。
保证最多 100 字段、50,000 行的单台账在内存中快速筛选。保证所有 50 个台账同时达到上限时仍无内存压力；系统必须配置总缓存预算。

3. 信息架构与管理界面

侧边导航在“知识管理”分组只增加一个 业务台账入口。该入口是台账列表；不新增平铺的“浏览 / 编辑 / 导入”导航项。新建台账仍从列表页发起，后续操作通过台账浏览页进入。

业务台账列表
新建、搜索、浏览→台账浏览页
筛选、分页、详情、行编辑→定义编辑 / Excel 导入 / JSON 导入导出
二级页面或对话框

浏览页是单台账的操作中心：上方保留“编辑定义”“导入 Excel”“导出”“新增数据”等动作；列表页不堆叠这些二级功能。

4. 数据定义

4.1 台账元数据

  • ledger_key：全局唯一、创建后不可修改的 slug；是 Profile 授权和 MCP 查询身份。
  • 名称、描述、状态、创建/更新时间、创建人、当前定义 revision、编辑并发 token。
  • 字段清单与可选的业务唯一键。唯一键可为一个或多个字段，用于 Excel 导入时识别更新；未配置时导入只能新增。

4.2 字段定义

字段说明
field_key不可变机器标识。显示名称可以修改；Excel 优先按 field_key 匹配，显示名称只在唯一时作为回退。
类型text、number、enum、date、datetime。是/否等语义使用枚举配置。
约束必填、枚举选项、默认值、显示顺序、唯一键成员。
查询/输出query_modes、sortable、agent_readable。未配置可查询的字段不得作为筛选、关键词或排序条件。

日期统一保存为 YYYY-MM-DD；日期时间以 UTC ISO 8601 保存。导入层负责把 Excel 日期单元格和明确格式的文本转换为统一类型。

5. 存储与内存快照

5.1 台账数据库

agent-bridge-datasets.db 保存定义与记录，不动态创建“每台账一张表”。核心表为：

  • business_ledgers：台账注册信息与当前定义 revision；
  • business_ledger_revisions：不可变定义快照、content_hash、version_hash、差异与操作者；
  • business_ledger_records：ledger_key、record_id、values_json、创建/更新时间与操作者；
  • business_ledger_imports：预览 token、源文件、列映射、校验结果、导入摘要及确认状态。

记录 JSON 保持数据模型简单、字段变更可控；由于查询不落 SQLite，不建立 EAV 索引或 FTS 索引。

5.2 缓存生命周期

SQLite 读取
定义 + 记录→类型校验与规范化
构建 DataFrame→原子发布
不可变快照→浏览 / MCP
只读查询
  • 应用启动后启动后台加载任务，按受控并发依次加载所有 active 台账；服务不因加载而阻塞就绪。
  • 未完成加载的台账查询返回 ledger_loading；不回退到 SQLite 查询，避免两条查询语义漂移。
  • 新增、编辑、删除、Excel 导入和定义变更必须先完成持久化校验，再构建完整新快照，最后以一次引用替换发布。读请求只能看见旧快照或新快照。
  • 一期选用 pandas，并在项目依赖中显式声明。数据量增长后可替换为 Polars；Service 接口不暴露 DataFrame 类型。
  • 设置全局 ledger_cache_max_bytes 与每台账行/字段硬上限。超过预算时拒绝导入或启用台账，而不是让进程 OOM。
50 个台账 × 50,000 行 × 100 个字段是理论上限而非可同时承诺的内存容量；缓存预算是避免“每个台账合法、整体失控”的必要护栏。

6. 查询语义

字段类型允许操作内存实现
文本exact、prefix、contains字面匹配；contains 使用 str.contains(..., regex=False, na=False)，不解释为正则。
枚举exact、in规范化后的相等或集合匹配。
数字exact、gt、gte、lt、lte、between数值列比较。
日期 / 日期时间exact、before、after、between已规范化的时间列比较。

一期多个字段条件仅支持 AND；每字段一个条件。关键词搜索仅作用于定义中同时允许 contains 与关键词检索的文本字段，语义为“任一允许字段包含关键词”。页面与 MCP 的过滤器共用同一个查询编译器。

7. 顶级 MCP 工具与 Profile 权限

7.1 工具契约

对 Agent 直接注册一个 request-scoped 顶级工具 query_business_ledger。它不通过通用 execute 提供，调用参数中也没有 service、tool_name 或 params 包装。

{
  "ledger_key": "asset_inventory",
  "filters": {
    "ip": {"op": "exact", "value": "10.0.0.8"},
    "operating_system": {"op": "in", "values": ["Linux", "Windows"]},
    "last_seen": {"op": "between", "from": "2026-08-01", "to": "2026-08-05"}
  },
  "keyword": "支付",
  "sort": {"field": "last_seen", "direction": "desc"},
  "limit": 50,
  "offset": 0
}

公共参数位于工具顶层；动态业务字段保留在 filters 对象中。完全平铺为 ip、name_like 等参数会让不同台账的静态 JSON Schema 失真，也无法统一表达枚举集合和范围条件。

7.2 Fail-closed 权限

  • 新增资源类型 business_ledger，复用 profile_resource_rules 的显式 allow-list。
  • MCP 调用必须带 active Profile；无 Profile 时台账不可用。
  • 生成 Profile 提示词时，仅注入已授权台账的 key、名称、描述、可查询字段、操作符和简短示例。定义或授权变化会失效该 Profile 的上下文缓存。
  • 若 ledger_key 不存在或未获授权，统一返回 ledger_not_available，并仅返回当前 Profile 已授权的台账概要；绝不列出或确认其他台账。
  • 执行时再次校验字段、操作符、排序与输出字段，不能因提示词遗漏或 Agent 伪造参数而绕过定义。

台账定义和数据维护操作由 BusinessLedgerService 与管理员 API 承担。管理 MCP 的契约可提前设计，但一期不注册给 Agent，也不进入普通 Profile 的工具目录。

8. Excel 与 JSON

8.1 Excel 维护

  1. 用户上传 xlsx，服务按 field_key 优先、唯一显示名称回退匹配列；
  2. 生成预览：未映射列、缺失必填字段、类型/枚举错误、唯一键冲突、将新增与更新的行数；
  3. 确认时重新核验定义 revision 和预览 token，任一变化则要求重新预览；
  4. 同一台账的整批写入使用一个 SQLite 事务；成功后构建并发布新缓存快照；
  5. 导出当前浏览筛选结果；包含 __record_id 以支持精确回写。

8.2 JSON 定义导入导出

定义格式为 agent-bridge.business-ledger、format_version: 1。定义导入与数据导入分开；覆盖前必须有差异预览。删除字段、修改字段类型或唯一键属于破坏性变更：若存在记录则拒绝直接覆盖，必须采用显式转换、清空确认或新建台账。

9. 版本与删除

  • 每次定义变化产生 revision。content_hash 表达执行语义，version_hash 表达含展示字段的完整历史；恢复任一历史定义会产生新的 revision。
  • 数据记录仅保存当前状态、创建/更新时间、操作者和导入批次，不做每次修改的全量版本副本。
  • 删除台账先停用并从缓存撤下，使其立即对 MCP 不可见；管理员确认后删除记录、定义和相关 Profile 资源规则。跨库清理由可重试的补偿任务完成。

10. 三库拆分

文件内容理由
data/agent-bridge.dbProfile、能力配置、知识、代码、记忆、工作流定义/任务/产物等主业务状态。小而稳定，主业务备份和分析不再携带大量运行事件。
data/agent-bridge-logs.dbtool_call_logs、agent_runs、script_runs、workflow_run_logs。高频追加、可按保留期清理的运行审计独立维护。
data/agent-bridge-datasets.db业务台账的定义、版本、记录、导入批次。Excel 数据与主业务隔离，可独立下载、备份、容量管理。

workflow_runs、workflow_node_runs 和 workflow_artifacts 一期留在主库：它们参与调度、增量复用和产物关联，跨库会显著弱化现有事务边界。

11. 迁移策略

  1. 升级前停止服务并建立可恢复备份；不得在 WAL 状态下直接移动单个数据库文件。
  2. 首次启动发现旧 wiki.db 且新主库不存在时，通过 SQLite backup API 写入临时 agent-bridge.db，校验后原子切换。
  3. 创建日志库并按主键/唯一 ID 分批、幂等复制运行日志表；记录迁移状态、行数和完成标记。
  4. 日志库校验完成后才切换读写。旧表在明确维护步骤完成前保留，允许失败恢复和重复迁移。
  5. 管理员确认后清理主库旧日志表，并用显式维护命令执行 VACUUM；不在服务启动路径做长时间压缩。
  6. 新建台账库并初始化其独立 schema；所有库都使用 WAL、busy_timeout、幂等 schema migration 与独立连接上下文。
现有 SQLiteStore 继续作为主库兼容门面；日志仓储改由独立 LogStore 连接，台账则由独立 BusinessLedgerStore/Service 承担。禁止通过 ATTACH 把三库伪装成单一事务。

12. 实施阶段与验收

阶段交付关键验收
1. 存储基座路径重命名、主/日志库拆分迁移、独立台账库和缓存生命周期。旧 wiki.db 可幂等升级；日志迁移失败可恢复；主库不再新增运行审计行。
2. 台账管理定义/记录 API、版本、唯一键、内存查询编译器。100 字段、50,000 行上限；写入后快照原子替换；日期和数字范围正确。
3. 管理页面列表页、浏览页、定义编辑、行编辑、Excel/JSON 预览导入导出。导航仅一个台账入口；破坏性定义变更明确拒绝或二次确认。
4. MCP 与权限顶级 query_business_ledger、Profile 上下文注入、资源规则接入。未授权台账不可发现、不可查询、错误中不泄露；仅一个 Agent 查询工具。
