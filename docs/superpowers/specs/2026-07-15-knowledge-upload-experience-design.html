知识库上传与文档浏览体验设计

覆盖上传进度、递归 ZIP、中文错误、ZIP/文件夹浏览、目录滚动、上传性能和同步任务实时刷新。

状态：已确认设计前端：Vue 3 + TypeScript后端：FastAPI + SQLite日期：2026-07-15

1. 目标与边界

上传弹窗是本次上传操作的唯一状态中心。上传过程中弹窗保持打开，展示每个顶层文件的网络上传进度和服务端处理阶段；失败项在弹窗内展开中文、可定位的错误详情。ZIP 按“整包原子”处理：外层 ZIP 或任意内层 ZIP 失败时，不为该 ZIP 创建任何文档、目录映射或同步任务。

ZIP 是用于浏览的特殊容器，不是检索后端的同步文档。ZIP 内的实际支持文档仍以普通文档入库、去重和同步；ZIP 本身不上传到 RAGFlow、WeKnora、PageIndex 或 Mock 后端，也不参与检索。

已确认的语义：一个上传动作可以包含多个普通文件和 ZIP。每个顶层 ZIP 自身原子失败；普通文件仍按文件独立处理。若一个 ZIP 中嵌套 ZIP 损坏，错误必须显示完整链路，例如“release.zip → manuals.zip → api-v2.zip”。

2. 当前根因

现象当前原因设计上的处理
没有上传进度客户端使用 fetch 提交 FormData，无法读取请求体上传进度；多个文件在前端串行发送。上传 API 客户端改为 XHR，可读取 upload.onprogress；普通文件受限并发。
嵌套 ZIP 失败extract_zip_documents 当前把任何 .zip 成员直接判定为不允许。递归读取 ZIP，先完成整棵压缩树的安全校验、CRC 校验和临时解压，再执行入库。
400 不友好后端错误可能是英文，客户端把整个响应体拼接成“400: ...”，没有提取 detail。后端错误统一中文且携带 ZIP 链路；客户端优先提取 JSON detail 并以中文标题显示。
文件名乱码ZIP 使用默认 CP437 解码，未标 UTF-8 的 GBK/GB18030 文件名被错误解释。按 UTF-8 标志优先，针对无标志名称在 UTF-8、GB18030、Big5、Shift-JIS、CP437 中选择可读编码。
右侧只有普通文件GET /docs 只返回文档行，目录只在左侧树中，ZIP 也没有持久化的容器关系。新增轻量 ZIP 虚拟树和浏览 API，右侧返回文件夹、ZIP 和文件三种条目。
目录撑开整体页面目录树没有固定可视高度，树的增长会影响详情页整体高度。目录树容器使用固定高度和 overflow-y:auto，页面只保留主内容滚动。
添加文档慢前端串行请求；普通文件先算一次 hash，归档时又算一次；ZIP 解压文件也会被重复读取。hash 结果向归档层传递；ZIP 解压复制时同步计算 hash；普通文件最多 3 路并发。
同步任务需刷新页面上传成功只刷新文档和知识库摘要，没有重新请求 /status 更新同步页签。上传、Git 同步、目录变更后统一刷新文档、目录、摘要和同步任务。

3. 整体架构

客户端

上传弹窗维护顶层上传项状态：queued、uploading、processing、succeeded、failed。XHR 只负责网络进度；请求完成前显示“服务端处理中”，避免把网络百分比误认为入库百分比。

服务端

普通文件沿用现有入库入口；ZIP 先递归验证与临时展开，生成虚拟浏览树，再调用复用 hash 的单文件入库流程。ZIP 错误在所有数据库写入之前抛出。

存储

现有 documents、document_versions 和 document_kbs 继续保存可检索文档。新增 knowledge_archive_entries 保存 ZIP、ZIP 内目录、嵌套 ZIP 和文件之间的浏览关系。

浏览

左侧仍是知识库真实目录树；右侧改用 browse API，当前真实目录下显示子目录、ZIP 容器和未归入 ZIP 的普通文件。进入 ZIP 后只切换浏览上下文，不改变同步任务模型。

4. ZIP 安全、递归和编码

4.1 递归规则

  1. 对每一级 ZIP 先读取成员清单，拒绝绝对路径、包含 .. 的路径、符号链接和重复的规范化路径。
  2. 对当前 ZIP 调用 testzip()，发现 CRC 或读取校验错误时立即终止，并把当前压缩链路加入错误信息。
  3. 普通支持扩展名文件写入临时目录；.zip 成员读取为内存流并递归处理。嵌套 ZIP 不作为普通文件。
  4. 全棵树成功后才调用文档入库；任意内层失败时临时目录清理，数据库中不出现本次 ZIP 的文档、虚拟节点或同步任务。
  5. 递归深度限制为 8 层；超过限制返回“ZIP 嵌套层级超过 8 层”，防止压缩炸弹消耗无限资源。该限制不影响普通目录深度。

4.2 文件名解码

若 ZIP 成员带 UTF-8 标志，使用 ZIP 标准解码结果；否则以可读性评分选择编码，候选顺序包含 UTF-8、GB18030、Big5、Shift-JIS 和 CP437。评分优先保留中文、日文等有效文字，惩罚控制字符、替换字符和典型 CP437 乱码符号。ASCII 名称在所有候选编码下保持不变。

如果任何候选都无法安全解码，错误中显示该 ZIP 的完整链路和“文件名编码无法识别”，不把乱码名称写进数据库。

4.3 错误格式

ZIP 上传失败
文件：release-assets.zip
位置：release-assets.zip → manuals.zip → api-v2.zip
原因：内层 ZIP 文件损坏，无法读取目录
处理结果：本次 ZIP 未新增任何文件

API 继续使用 HTTP 400 表示用户上传内容不合法，但响应体的 detail 是上述中文信息；客户端不再直接展示英文状态文本。

5. ZIP 虚拟浏览树

5.1 数据模型

新增表 knowledge_archive_entries。每行代表一个浏览条目，kind 为 zip、folder 或 document。外层 ZIP 的父级是知识库真实目录（parent_folder_id）；ZIP 内的条目通过 parent_id 形成树。文件条目通过 doc_id 指向现有文档实体。

knowledge_archive_entries
  id              INTEGER PRIMARY KEY
  kb_id           INTEGER NOT NULL
  parent_id       INTEGER NULL       -- ZIP 内部父条目
  parent_folder_id INTEGER NULL      -- 仅外层 ZIP 使用
  kind            TEXT NOT NULL      -- zip | folder | document
  name            TEXT NOT NULL
  relative_path   TEXT NOT NULL
  doc_id          INTEGER NULL
  status          TEXT NOT NULL DEFAULT 'active'
  created_at      TEXT NOT NULL
  updated_at      TEXT NOT NULL

为支持“ZIP 内文档只在 ZIP 浏览上下文出现”，document_kbs 增加可空的 archive_entry_id。普通上传为空；ZIP 首次导入的文档指向对应文件条目。重复内容复用已有文档时，新 ZIP 文件条目仍可指向该文档，但不移动已有文档的原始目录位置。

解压成功后的整批入库使用 SQLite 单事务：文档、版本、知识库关联、虚拟节点和同步任务要么全部提交，要么全部回滚。归档文件采用回滚清理清单，只有本批次新写入且回滚后没有任何版本引用的内容寻址文件才会删除，避免产生半成品状态。

5.2 浏览 API

新增 GET /kbs/{kb_slug}/browse。folder_id 和 archive_entry_id 二选一；不传参数时进入知识库根目录。返回当前上下文和直接子条目：

{
  "context": {"kind": "folder", "id": 12, "name": "产品文档", "parent_id": null},
  "entries": [
    {"kind": "folder", "id": 21, "name": "API", "child_count": 4},
    {"kind": "zip", "id": 88, "name": "release-assets.zip", "child_count": 12},
    {"kind": "document", "doc_id": 31, "slug": "readme", "name": "readme.md", "sync_status": "synced"}
  ]
}

右侧点击真实目录条目时选择该目录；点击 ZIP 或 ZIP 内目录时仅更新 browse 上下文；点击文件沿用现有文档详情。面包屑显示“知识库 / 真实目录 / ZIP / 内部目录”，返回按钮回到上一级上下文。

6. 上传弹窗与进度

  • 弹窗宽度保持可读范围，文件名列使用可收缩的 minmax(0,1fr)，长路径通过 title 或详情展示，不撑破布局。
  • 上传开始后禁用关闭和重新选择；取消按钮只在队列尚未开始时可用。服务端处理完成后显示成功/失败汇总，用户点击“关闭”退出。
  • 每个顶层项显示文件名、大小、进度、阶段和错误详情；ZIP 额外显示“解压中”“解析内层 ZIP”“创建浏览目录”等阶段。
  • 普通文件请求最多并发 3 个；同一个 ZIP 请求不拆分，保证一个 ZIP 的原子性。上传成功后重新加载知识库摘要、目录树、右侧 browse 条目、当前文档列表和同步任务列表。
  • 上传错误通过客户端统一解析：优先读取 JSON 的 detail，其次尝试纯文本，最后才使用“上传失败（HTTP 状态码）”。

7. 性能设计

优化点实现收益与约束
避免普通文件二次 hashArchiveStorage.store(source, content_hash=..., file_size=...) 接收调用方已计算的结果。每个文件从两次读降为一次 hash + 一次归档复制；内容去重逻辑不变。
ZIP 解压同时计算 hash写临时文件时使用 hash wrapper，ExtractedDocument 携带 hash 和大小。ZIP 子文件不再为去重额外完整读取一次；仍保留临时文件供归档复制。
前端受限并发普通文件 3 路并发，单个 ZIP 作为一个请求；每项独立显示进度。减少大量小文件的网络等待；不把 SQLite 写入并发扩大到不可控范围。
数据库索引为 knowledge_archive_entries(kb_id,parent_id,status)、(kb_id,parent_folder_id,status) 和 document_kbs(archive_entry_id) 建索引。右侧浏览只扫描当前父节点，避免每次加载整棵树。

本次不引入后台上传任务、WebSocket 或 SSE；这样保留现有 API 兼容性，网络进度和服务端阶段反馈已经能覆盖用户可感知的等待过程。未来若需要跨刷新保留上传任务，再单独引入异步任务模型。

8. 同步任务刷新

抽取统一的前端刷新函数，在以下操作成功后调用：

  1. 上传完成：刷新知识库摘要、目录树、browse 条目、当前文档和当前知识库的同步任务。
  2. Git 数据源同步或删除：刷新数据源、文档、摘要和同步任务。
  3. 目录创建、重命名、移动、删除以及文档移动/关联：刷新目录、browse 条目、文档和同步任务。

同步页签数量以最新 GET /status 响应为准，不依赖整页刷新。已经运行或失败的任务继续由后端状态返回，前端只负责重新拉取和展示。

9. 测试与验收

ZIP / 编码

  • 递归导入两层以上 ZIP。
  • 损坏内层 ZIP 返回完整链路且 KB 无新增文档。
  • GBK/GB18030 中文文件名可读；路径安全和符号链接继续拒绝。
  • ZIP 虚拟树可浏览外层、内部目录、嵌套 ZIP 和文件。

上传 / 性能

  • XHR 进度事件更新每个上传项。
  • 普通文件并发上限为 3，失败项显示中文原因。
  • hash 只计算一次；ZIP 成员不重复读取。
  • 上传弹窗状态和完成汇总正确。

浏览 / 目录

  • 右侧同时显示文件夹、ZIP 和普通文件。
  • 目录树固定高度，超出后内部滚动。
  • ZIP 图标与普通文件图标区分，点击进入内容。
  • 删除文档/目录后不留下失效虚拟节点。

同步 / 回归

  • 上传后同步页签立即显示新增任务。
  • 已有去重、目录、Git、后端同步测试继续通过。
  • 普通文件和 ZIP 的旧 API 响应兼容。
  • 前端 typecheck、build 与聚焦 Node 测试通过。

10. 不做的事情

  • 不把 ZIP 原始二进制作为检索文档上传到任何后端。
  • 不在本次引入后台异步上传任务、断点续传、跨刷新恢复。
  • 不改变现有内容去重范围：仍按知识库内当前版本的 SHA-256 判断。
  • 不把普通真实目录和 ZIP 虚拟目录混为同一个后端目录；ZIP 仅作为浏览容器，文档同步路径沿用文档内部相对路径。
