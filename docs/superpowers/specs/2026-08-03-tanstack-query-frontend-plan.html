TanStack Query 前端渐进式改造计划

范围：frontend/capabilities 的服务端读取、缓存、失效与运行态轮询。计划不改变 API 契约、工作流业务语义或编辑器本地状态模型。

决策：引入 @tanstack/vue-query，但只作为 server state 层。先完成观测与运行态页面，再迁移工作流和知识管理的读取路径；表单草稿、Vue Flow 画布、上传进度和弹窗仍由现有 Vue composable 管理。

现状与目标

  • src/api/client.ts 约 920 行，集中封装了大量接口，但 GET 请求均为 cache: 'no-store'，无客户端查询缓存与取消语义。
  • 日志、Agent Run、工作流产物等页面各自维护 loading、错误回退、请求 token 和定时器。典型位置包括 LogsView.vue、AgentRunsView.vue、useWorkflowArtifacts.ts 和 useWorkflowRunProgress.ts。
  • 目标是消除重复的异步读取样板代码，做到按 query key 去重、在路由返回时复用短时缓存、写入后精确失效，以及只对运行中任务条件轮询。

边界与非目标

纳入不纳入
GET 查询、详情按需加载、分页/筛选、运行状态轮询、写后失效后端 API 路由、数据模型、工作流调度和 SSE 协议改造
读取请求的 AbortSignal 透传Vue Flow 节点、表单草稿、上传百分比、导航离开守卫和确认弹窗的状态迁移
保留手动“刷新”按钮，改为 refetch通过 Query 隐藏写操作失败、或对所有 mutation 做乐观更新

阶段 0：基础设施

  1. 新增 @tanstack/vue-query 依赖，在 src/main.ts 安装单例 VueQueryPlugin 和 QueryClient。
  2. 新增 src/lib/query.ts：统一 query key 工厂、客户端默认项和可复用的错误提示转换。key 必须以资源域开头并包含会影响结果的全部参数，例如 ['agent-runs', 'list', filters] 与 ['workflow-runs', runId, 'events']。
  3. 全局采用保守默认：staleTime: 15_000、gcTime: 300_000、retry: false、refetchOnWindowFocus: false。稳定配置类数据按 query 覆盖到 60 秒；运行中资源自行开启条件轮询。
  4. 为 api/client.ts 底层读取方法增加可选 signal，并在首批查询接口透传 TanStack 提供的 signal。保持现有调用兼容，mutation 不自动重试。

阶段 1：优先迁移观测与运行态页面

范围改造方式失效/轮询策略
LogsView.vue筛选和分页仍用 ref；防抖后的搜索词进入 query key；列表和详情分别使用 useQuery。手动刷新调用 refetch；不在焦点恢复时自动刷新，避免覆盖用户筛选体验。
StatsView.vue维度作为 query key 的一部分，删除手工 loading 与 loadStats。维度切换自然形成新缓存项；手动刷新只刷新当前维度。
AgentRunsView.vue列表、单次运行、事件、payload、子 Agent 详情拆成独立查询；删除列表请求 token。仅当详情状态为 running 时，每 1.5 秒刷新运行和事件；结束后停止。停止运行 mutation 成功后失效该运行、事件和列表。

阶段 2：工作流读取层

  1. 先在 useWorkflowArtifacts.ts 中迁移产物搜索、详情和历史；查询 key 必须覆盖 profile、workflow、搜索词、路径、格式、页码和页大小。
  2. 在 useWorkflowRunProgress.ts 迁移运行概览、运行详情、日志、事件和 Agent Run 关联信息。保留现有进度视图选择状态、批量队列和路由跳转。
  3. runWorkflow、stopWorkflowRun、任务执行/重置成功后，精确失效 workflow-runs、当前 run、事件、关联 Agent Run 和产物列表；不以“全局刷新”替代失效。
  4. 暂不整体迁移 2,000 余行的 WorkflowView.vue。仅让它消费 composable 暴露的 query 状态，待阶段 2 稳定后再评估其余静态资源读取。

阶段 3：稳定配置与知识管理页面

  • 迁移服务、Profile、脚本、Skill、后端、代码仓库和知识库列表/详情等读取路径。配置写入成功后失效所属列表和详情，不采用普遍乐观更新。
  • 知识库目录/浏览结果的 key 必须包含 kbSlug、目录与压缩包上下文；文档上传仍保留 useKnowledgeUploadQueue，完成后只失效当前知识库的相关目录、文档和同步状态。
  • Dashboard 的“服务后逐项加载工具数”属于 API 聚合问题，不将 Query 作为 N+1 的替代方案；单独评估是否增加摘要字段或聚合接口。

测试与验收

  1. 为 query key 工厂、条件轮询判定和 mutation 失效范围补充单元测试；用 mock API 验证切换筛选时旧响应不会覆盖新数据。
  2. 为首批三个页面补充组件行为测试：首次加载、错误、手动刷新、分页/搜索、防抖、详情打开以及运行结束后停止轮询。
  3. 验证路由往返：短时返回复用缓存；显式刷新和成功 mutation 后始终读取新数据；离开页面后 observer 停止，未完成请求可被取消。
  4. 每阶段运行 cd frontend/capabilities && npm run check。阶段 2 完成后再运行相关后端/API 测试，确保前端未改变 API 语义。

实施顺序与提交策略

提交 1依赖、QueryClient、key 工厂与读取 signal 兼容层。
提交 2Logs、Stats、Agent Runs 迁移及测试。
提交 3工作流产物与运行进度迁移及测试。
提交 4+按领域迁移稳定配置和知识管理读取路径。

每个提交独立可运行；若阶段 1 的刷新、筛选或轮询行为不满足验收，停止扩展迁移并先修复基础设施。
