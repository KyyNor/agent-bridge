Agent Bridge x claude-mem 集成设计

目标：把 claude-mem 集成为 Agent Bridge 的记忆引擎，同时保持 Agent Bridge 作为 UI、profile、hook 注入、MCP 门面的控制平面。

决策：采用混合收敛方案，不 fork claude-mem，不改 claude-mem 内部 schema。

控制平面

Agent Bridge 管理 memory block、profile 绑定、Claude Code hooks、服务端代理接口、健康状态和 MetaMCP 直出工具。

记忆引擎

claude-mem 保持负责 worker、观察写入、压缩、存储、检索与上下文生成。

隔离模型

每个 memory block 映射独立 CLAUDE_MEM_DATA_DIR，服务端目录不暴露给 CLI。

1. 背景与范围

docs/TODO.md 已确定 claude-mem 集成方向：Agent Bridge 负责控制平面，claude-mem 负责 worker、压缩、存储和检索。第一阶段不 fork claude-mem，不重写其 native schema，通过 worker API 与 hook 行为完成闭环验证。

本设计覆盖后端 schema、服务层、CLI hook wrapper、Claude Code hook 注入、MetaMCP 工具、前端管理台和失败降级策略。实现计划另行编写。

关键修正

Hook 命令不能直接访问服务端目录，也不能由 CLI 直接调用 claude-mem worker。CLI 与服务端最终可能不在同一台机器，因此 CLI hook wrapper 只把 Claude Code payload 发送给 Agent Bridge 服务端，由服务端解析 profile、定位 memory block、托管或调用 claude-mem worker。

2. 已确认决策

主题 决策 理由
总体方案 混合收敛：Agent Bridge 控制平面 + claude-mem 记忆引擎 实现量可控，保留 claude-mem 能力，不把外部 schema 变成 Agent Bridge 的维护负担。
数据隔离 每个 memory block 一个独立 CLAUDE_MEM_DATA_DIR 避免 profile 作用域、project 作用域和 claude-mem 默认 project 作用域混乱。
Hook 行为 数量、事件、matcher、timeout 与 claude-mem 原始 hooks.json 保持一致 降低行为偏差，保持 claude-mem 原有写入、上下文、总结时机。
Hook 命令 只把命令入口改为 agent-bridge memory hook claude-code <action> Claude Code 调本地 CLI；本地 CLI 再调服务端，服务端执行真实处理。
MCP 暴露 Agent 只使用 Agent Bridge MetaMCP 的 memory_search、memory_timeline、memory_get 避免用户同时面对 Agent Bridge MCP 与 claude-mem MCP 两套入口。

3. 系统边界

Agent Bridge 负责

  • 管理 memory block 的创建、列表、详情、状态和健康信息。
  • 管理 profile 到 active memory block 的单选绑定。
  • 在 profile use 时幂等写入 MetaMCP 配置、profile 指针和 Claude Code hooks。
  • 提供瘦 CLI hook wrapper，把 hook payload 发送到服务端。
  • 服务端按 memory block 解析 CLAUDE_MEM_DATA_DIR 并代理 claude-mem worker。
  • 在 MetaMCP 暴露稳定的 memory 工具契约。

claude-mem 负责

  • worker 服务和原始 hook action 行为。
  • 观察写入、文件上下文、会话初始化、总结和压缩。
  • 底层存储、检索、timeline 与 observation detail。
  • 内部 schema 与数据格式演进。

4. 数据模型

memory_blocks

CREATE TABLE IF NOT EXISTS memory_blocks (
  block_key TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'active',
  data_dir TEXT NOT NULL,
  worker_base_url TEXT,
  last_health_json TEXT NOT NULL DEFAULT '{}',
  created_by TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

profile_memory_bindings

CREATE TABLE IF NOT EXISTS profile_memory_bindings (
  profile_key TEXT PRIMARY KEY REFERENCES project_profiles(profile_key) ON DELETE CASCADE,
  block_key TEXT REFERENCES memory_blocks(block_key) ON DELETE SET NULL,
  enabled INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

data_dir 默认由服务端生成：AGENT_BRIDGE_ROOT/data/claude-mem/blocks/<block_key>/。CLI 不读取、不写入、不推导这个目录。

profile 绑定不放入 profile_resource_rules。后者表达“某 profile 可访问哪些资源”；active memory block 是运行时默认记忆落点，语义不同。

5. 服务与模块

模块 职责
memory_management/service.py MemoryService：memory block CRUD、profile 绑定、search/timeline/get 聚合、权限判断。
memory_management/claude_mem/client.py ClaudeMemClient：封装 claude-mem worker HTTP 调用与响应归一化。
memory_management/claude_mem/worker.py ClaudeMemWorkerService：发现安装、按 block 启动 worker、健康检查、端口缓存、版本状态。

cli/memory.py 瘦 CLI：从 stdin 读取 hook payload，POST 服务端，输出服务端返回的 hook stdout。
cli/profile.py profile use 扩展：按原版 claude-mem hook 配置写入 Agent Bridge hook command。

7. Claude Code hooks

Agent Bridge 写入的 hook 数量、事件、matcher 与 timeout 保持和 claude-mem 原始 plugin/hooks/hooks.json 一致，只替换 command。原始配置来源：claude-mem hooks.json。

事件 Matcher Action Timeout
Setup*version-check300
SessionStartstartup|clear|compactstart60
SessionStartstartup|clear|compactcontext60
UserPromptSubmit无 matchersession-init60
PostToolUse*observation120
PreToolUseReadfile-context60
Stop无 matchersummarize120

命令模板

agent-bridge memory hook claude-code <action> \
  --profile <profile_key> \
  --server-url <agent_bridge_base_url> \
  --event <event_name> \
  --matcher <matcher_if_any>

Hook command 不固化 block_key。服务端每次按 profile_key 解析当前 active memory block，因此 UI 修改绑定后，无需立刻重新运行 profile use 才能生效。

配置文件位置

  • profile use --scope project：写当前项目 .claude/settings.local.json。
  • profile use --scope user：写 ~/.claude/settings.json。
  • 只管理 Agent Bridge 自己的 command，不删除用户手写 hooks。

Claude Code hook 通过 stdin 向 command 传入 JSON payload；hook command 可返回 JSON 控制是否继续、是否抑制输出等行为。参考：Claude Code Hooks 文档。

8. Hook 调用链

1Claude Code 触发原版事件，如 PostToolUse。
2本地执行 agent-bridge memory hook claude-code observation。
3CLI 从 stdin 读取 payload，POST 到服务端 hook API。
4服务端按 profile 解析 active block，并设置 block 的 CLAUDE_MEM_DATA_DIR。
5服务端调用或代理 claude-mem worker，返回兼容 Claude Code 的 hook stdout。

CLI 降级

如果 CLI 无法访问 Agent Bridge 服务端，默认输出：

{"continue":true,"suppressOutput":true}

并以 exit code 0 退出，避免网络问题阻断 Claude Code 主流程。

服务端降级

  • profile 不存在或停用：返回 no-op，并记录健康状态。
  • profile 未绑定 block：返回 no-op，状态为 not_configured。
  • worker 未安装、依赖缺失、版本过旧、启动失败：返回 no-op 或 claude-mem 兼容错误响应，默认不阻断 Claude Code。
  • context 与 file-context 这类会影响 Claude Code 输出的 action，需要优先保持 claude-mem 原版 stdout contract。

9. Worker 管理与健康状态

第一阶段采用轻量服务端托管：按需启动、健康检查、端口缓存、失败降级，不做复杂 supervisor。

状态 含义
not_configuredprofile 未绑定 memory block。
claude_mem_not_installed服务端未发现 claude-mem plugin scripts 或 worker 入口。
dependency_missing服务端缺少 Node、Bun、uv 或 claude-mem 需要的运行时依赖。
worker_starting服务端正在为 block 启动 worker。
worker_readyworker 可用，检索与 hook action 可执行。
worker_errorworker 启动或请求失败。
version_outdated检测到 claude-mem 版本过旧。

服务端启动 worker 时注入 CLAUDE_MEM_DATA_DIR=<block.data_dir>。如果 claude-mem worker 本身要求端口发现文件或动态端口，Agent Bridge 负责在服务端侧缓存和复用，不暴露给 CLI。

权限策略

  • 普通 profile 只能访问自己绑定的 active memory block。
  • block 参数第一阶段仅用于 admin/debug；非 admin 传非绑定 block 时返回 profile policy error。
  • profile 未绑定 block 时返回 {"status":"not_configured","items":[]}，不抛硬错误。

13. 测试策略

  • Storage：memory block CRUD、profile binding 唯一约束、删除 block 后 binding 行为。
  • Service：profile 未绑定、绑定 disabled block、admin explicit block、worker 不可用降级。
  • Hook CLI：stdin payload 透传、服务端返回 stdout 原样输出、服务端不可达 no-op。
  • Hook 注入：从 claude-mem 原始 hook specs 生成 Agent Bridge command，保持事件、matcher、timeout 不变；不删除用户 hooks。
  • MCP：memory_search、memory_timeline、memory_get 的 profile 作用域与 not_configured 响应。
  • API：memory routes 和 profile memory routes。
  • Frontend：列表、创建、绑定、搜索调试的基础交互测试。

14. 风险与取舍

Hook stdout contract 是最高风险点

context 与 file-context 会影响 Claude Code 行为。实现时应优先用集成测试固定 stdout，不要在第一阶段擅自改写 claude-mem 的返回语义。

  • 远程 CLI 网络失败：默认 no-op，避免阻塞 Claude Code，但会导致某些记忆写入缺失；需要在 UI health 中可见。
  • worker 端口发现：服务端负责，CLI 不参与；实现时要避免同 block 多 worker 竞争。
  • 敏感信息：第一阶段保留 claude-mem 原有过滤能力；Agent Bridge 仅在服务端代理层补充必要 metadata。更细粒度过滤放第二阶段。
  • 成本模型：observer LLM 调用成本先在 health/metadata 中曝光，完整统计放第二阶段。
  • SQLite 写入压力：TODO 中的 WAL 模式应作为前置或同期工作，降低 hook 高频状态更新带来的锁冲突。

15. 分阶段交付

第一阶段：闭环验证

  • SQLite WAL。
  • memory schema、repository、service、API。
  • profile memory binding。
  • hook 配置一比一替换 claude-mem 原始 hooks。
  • CLI 瘦 wrapper 到服务端 hook API。
  • 服务端按 block 托管/代理 claude-mem worker。
  • MetaMCP 三个 memory 工具。
  • 基础 UI。

第二阶段：产品化

  • claude-mem 版本兼容矩阵和安装向导。
  • memory block 迁移、备份、归档。
  • 敏感字段过滤与截断策略 UI。
  • 成本观测与 token/observer 调用统计。
  • 更精细的启动上下文策略和检索质量调试。

16. 验收标准

  • 创建 memory block 后，服务端 data dir 位于 AGENT_BRIDGE_ROOT/data/claude-mem/blocks/<block_key>/。
  • profile 最多绑定一个 active memory block，UI 与 API 都能查看和修改。
  • profile use 写入的 Claude Code hooks 与 claude-mem 原始事件、matcher、timeout 一致，command 改为 Agent Bridge CLI。
  • Hook CLI 不访问服务端本地目录；服务端不可达时不会阻断 Claude Code。
  • 服务端 hook API 能按 profile 解析 block，并调用对应 claude-mem worker。
  • MetaMCP 暴露 memory_search、memory_timeline、memory_get，profile 未绑定时返回 not_configured。
  • worker 缺失、依赖缺失、版本过旧、启动失败在 UI health 中可见。
