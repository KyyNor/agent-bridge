工作流增量执行与历史产物复用设计

采用“整体 workflow revision + 自动节点指纹 + stale 任务状态 + 每次 run 独立记录”的增量执行方案。

核心结论：stale 让同一 task_key 下按 set_at 最新的任务版本重新进入队列；planner 决定节点复用或重跑；output_json 作为结构化节点缓存；历史 run 和 artifact 保持只读。

1. 版本层次

版本含义作用
task_version任务业务版本必须严格一致，不能跨任务版本复用
workflow_revision_no工作流整体修订号触发增量计划重算
节点语义指纹节点执行语义及资源版本判断节点本身是否变化
输入/依赖指纹任务、上游输出、入边和条件判断节点输入是否变化

节点不维护人工版本号。节点 ID 单独校验；位置和纯展示名称不参与执行语义指纹。

2. stale 状态

pending 和 stale 都可领取，pending 优先。工作流 revision 变化时，同一 task_key 只选择 set_at 最新的任务版本进入 stale；旧 task version 即使 completed，也保持 completed。

pending → running → completed
stale   → running → completed
running → failed / abandoned
completed → stale（最新任务版本且 workflow revision 变化）

3. 增量计划

每次执行前生成不可变的 IncrementalPlan。预览和真实执行使用同一个 planner。默认以同一 workflow、profile、task key、task version 下最近成功的 run 作为单一基准；基准整体不可用时才回退到更早成功 run，不在多个 run 之间逐节点拼接。

节点只有在节点 ID、类型、语义指纹、输入指纹、依赖指纹、历史成功状态、output hash、artifact 有效性和 runtime 兼容性全部满足时才复用。一个节点重新执行，会向所有下游传播影响。

4. 缓存与运行隔离

当前系统已经持久化 workflow_node_runs.output_json、workflow_runs.output_json 和 workflow_artifacts.content，但 executor 目前不会读取历史输出。改造后，复用节点在当前 run 建立自己的 node run，复制完整 output_json，记录来源 run/node/revision，并注入当前执行上下文。

数据库 artifact 可按 artifact ID 只读引用；历史 run 目录中的文件必须在当前 run 中重新物化。历史 run 和 artifact 不覆盖，当前 run 只写自己的记录。

5. 数据和接口

workflow_runs 增加 workflow revision、task version、execution mode、source run 和 plan 信息；workflow_node_runs 增加指纹、执行/复用模式、判断原因和来源字段；artifact 增加 producer/source/validity 信息。

新增运行预览接口，现有运行接口支持 auto、incremental、force_full。页面运行按钮默认按任务状态选择普通执行或增量执行；当前 revision 已完成的任务展示已有结果并提供强制全量选项；artifact 列表通过 lineage 找到同一运行入口。

6. 一致性与验收

  • 计划创建前后使用 workflow revision CAS；revision 变化则重新规划。
  • 复用前二次校验 source run、output hash、artifact hash、任务版本和 profile。
  • stale 运行失败后保持 stale，超过尝试次数才进入 abandoned。
  • 强制全量不读取历史节点输出。
  • 覆盖节点修改、边/条件变化、节点新增/删除、历史产物缺失、任务版本变化、多版本按 set_at 选择、并发运行和预览一致性。
