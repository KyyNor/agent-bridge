Agent Bridge Report Draft

从分散知识管理到统一 Agent 能力平面

本材料用于说明 Agent Bridge 的建设逻辑：不是再做一个孤立知识库，也不是简单聚合几个工具， 而是把部门已有的模型基础设施、知识库、代码资产和 MCP 工具组织成可组合、可复用、可治理的能力平面， 让 Claude Code 等 Agent 可以通过统一入口安全稳定地使用部门能力。

定位：Agent 能力平面 入口：Claude Code / MetaMCP 基础设施：vLLM / LiteLLM / TEI 内置能力：Wiki / CodeGraph
建设背景 核心判断 总体架构 Agent Bridge 使用流程 建设价值 后续规划 汇报口径

1. 建设背景：部门不是缺知识，而是缺统一组织方式

过去的知识、工具、文档和项目经验都存在，但它们分布在不同系统和个人流程中，难以稳定复用。

Problem

过去的状态

  • 文档、接口说明、项目经验散落在不同位置。
  • 数据库、API、代码仓库、知识库各自维护。
  • 每个 Agent 或项目都需要重复手写接入配置。
  • 能力可见范围、调用日志和失败归因缺少统一治理。
  • 结构化知识容易被文档化，失去实时性和可执行性。

目标状态

  • 所有能力进入统一目录，可注册、可搜索、可调用。
  • Agent 只接入一个统一 MetaMCP 网关。
  • 按项目 Profile 控制可见能力和资源范围。
  • 知识库、代码图谱、外部 MCP 工具统一治理。
  • 调用全链路可审计、可统计、可定位问题。

2. 核心判断：单纯建设知识库不够，需要能力平面

Agent 需要的不只是“能检索文档”，还需要准确调用结构化接口、理解代码、访问项目授权范围内的工具。

Judgement
知识库负责“读懂文档”，MCP / CodeGraph 负责“查准结构和执行约束”，Agent Bridge 负责统一入口、治理和编排。

文档型知识

制度、手册、方案、PDF、历史材料，适合进入知识库，通过 Embedding、Rerank 和 RAG 召回。

结构化知识

服务目录、接口契约、SQL、数据血缘、项目元数据，适合通过 MCP 保留参数化查询能力。

代码知识

仓库、模块、文件、符号、调用链和影响面，适合通过 CodeGraph 暴露给 Agent。

执行型能力

查询、分析、同步、检查、生成等能力，需要统一注册、风险分级、权限控制和调用审计。

3. 总体架构：四层组织 Agent 基础设施

把用户交互、能力治理、知识工具和模型基础设施解耦，各层职责清晰。

Architecture
用户交互层

Claude Code 是用户实际交互的 Agent。用户在项目中提出问题或任务，不需要理解背后的模型、知识库和工具分布。

能力平面层

Agent Bridge 提供统一 MetaMCP 网关、能力注册中心、Project Profile、调用日志和管理控制台。

知识与工具层

Wiki 知识库、CodeGraph 代码图谱、外部 MCP 服务、业务 API、数据库查询工具等都被抽象为能力来源。

模型基础设施层

vLLM 提供推理服务，LiteLLM 提供模型统一路由，TEI 提供 Embedding 和 Rerank 能力，支撑知识检索和问答效果。

4. Agent Bridge 做什么：把能力变成可治理资产

Agent Bridge 的重点不是替代已有系统，而是把已有系统纳入统一能力目录和治理闭环。

Capability Plane

能力注册

登记外部 MCP 服务、Wiki 知识库、CodeGraph 仓库，形成统一能力目录。

能力发现

通过 MetaMCP search 让 Agent 像浏览目录一样发现当前项目可用能力。

能力调用

通过 MetaMCP execute 执行只读类工具，保留参数、Schema、返回结果和错误信息。

项目治理

通过 Project Profile 控制不同项目可见的 MCP 服务、KB 和代码仓库。

审计观测

记录谁在什么时候调用了什么能力，是否成功，失败发生在哪个阶段。

内置能力

Wiki 和 CodeGraph 作为平台固有能力，不再以临时工具方式分散接入。

5. 典型使用流程：从项目接入到能力调用

目标是让 Agent 使用能力的过程变得稳定、可控、可复用。

Workflow
1. 管理员注册能力 登记 MCP 服务、知识库、代码仓库，并同步工具清单或索引状态。
2. 创建项目 Profile 按项目配置可访问的服务、KB、Repo 和资源范围。
3. Claude Code 接入 项目只配置一个 Agent Bridge MetaMCP 地址，并携带对应 Profile。
4. Agent 搜索与调用 Agent 先 search 发现能力，再 execute 调用授权范围内的工具。
5. 平台记录审计 记录调用日志、耗时、结果、失败阶段和责任方，支撑排障和运营。

6. 建设价值：从一次性接入变成长期运营

平台价值不是“多一个入口”，而是把知识和工具变成可以沉淀、复用、度量和治理的部门资产。

Value
价值方向 解决的问题 带来的变化
统一入口 各 Agent 分别配置工具、知识库和模型能力。 Claude Code 等 Agent 只接入 Agent Bridge，一次接入，多处复用。
统一资产 文档、接口、代码、工具分散，无法形成能力目录。 所有能力都可以注册、分类、搜索、调用，成为可运营资产。
统一治理 项目之间缺少清晰的能力边界和数据边界。 通过 Profile 控制不同项目能看什么、能用什么。
统一观测 调用失败后难以判断是 Agent、平台、权限、MCP 还是后端问题。 通过日志、统计、失败归因定位问题责任方。
统一演进 每次新增模型、知识库或工具都要重复接入。 新增能力只需要纳入平台，已有 Agent 和项目可以按治理规则复用。

7. 后续规划：从能力目录走向能力运营

基础能力打通后，下一步重点是提升检索效果、治理深度和运营可见性。

Roadmap

检索策略运营

完善 KB 默认后端、Embedding / Rerank 策略、Profile 级检索覆盖配置，让知识效果可配置、可评估。

观测与报表

增强调用统计、时间趋势、慢调用分析、失败归因和审计导出，支持平台运营。

Action 工具治理

对有副作用的工具引入风险分级、确认、审批、dry-run 和回滚策略。

工作流编排

把文档入库、代码同步、质量检查、能力评测等流程沉淀成可复用工作流。

8. 汇报口径：一句话与三句话

用于开场、结尾或向领导解释项目定位。

Talking Points
一句话定位

Agent Bridge 是部门面向 Agent 的统一能力平面，把模型、知识库、代码仓库、MCP 工具和项目权限组织起来， 让 Claude Code 等 Agent 能够按项目安全、稳定、可审计地复用部门能力。

三句话说明

第一，部门过去的问题不是没有知识，而是知识和工具没有统一沉淀为可复用能力。 第二，单纯做知识库无法覆盖接口、代码、结构化数据和执行工具，所以需要能力平面。 第三，Agent Bridge 通过统一注册、发现、调用、治理和审计，让 Agent 能力建设从零散接入变成长期运营。
