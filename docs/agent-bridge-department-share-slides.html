Agenda

今天不按功能清单讲，按一个故事讲

开场建议：先告诉大家这不是一次系统操作培训，而是一次“以后我们怎么把经验交给 Agent 使用”的讨论。
Act 1 · The Pain

先从一个普通问题开始

如果明天一个新同事接手一个项目，他想搞清楚一个接口怎么用、相关文档在哪、代码里谁调用了它，现在会怎么做？

  • 先问群里有没有文档，得到几个不同链接。
  • 翻 Wiki、README、历史方案，发现版本不一定一致。
  • 去代码仓库里搜索关键词，再问熟悉的人确认。
  • 想让 Agent 帮忙，但 Agent 并不知道这些内部资料在哪。
  • 最后问题解决了，路径却没有沉淀，下次还要再来一遍。
这里可以现场问一句：大家现在找部门知识，第一反应是去哪里？让大家说几个入口，制造共鸣。
What Is Broken

我们不是没有知识，而是没有把知识组织成能力

Fragmented

入口分散

文档、接口、代码、工具、模型各有入口，靠人记忆串起来。

Repeated

重复接入

不同项目、不同 Agent 反复写配置、接服务、维护说明。

Unclear

边界不清

谁能看哪个知识库，哪个项目能用哪个工具，没有统一规则。

Invisible

过程不可见

调用失败后，不知道是权限、工具、知识库、模型还是平台问题。

真正的问题不是“知识在哪里”，而是“Agent 能不能稳定、合规、可复用地使用这些知识和工具”。
从知识管理问题，升级为 Agent 能力治理问题。
Act 2 · The Turn

关键转折：不要只做知识库，要做能力平面

1

文档型知识进入知识库

制度、手册、方案、PDF、历史资料适合通过 Embedding、Rerank 和 RAG 检索。

2

结构化能力保留接口

服务目录、接口契约、SQL、数据血缘、项目元数据，应该通过 MCP 保留可查询、可约束、可执行的形态。

3

代码知识交给 CodeGraph

代码仓库、文件、符号、调用链、影响面分析，需要结构化索引，而不是只把代码文档化。

知识库负责“读懂文档”，MCP / CodeGraph 负责“查准结构和执行约束”，Agent Bridge 负责统一入口、治理和编排。
这页是整场汇报的立论。
Act 3 · Live Demo

现场演示只演一个闭环

不要把演示做成“功能逐个点”。用一个任务贯穿：发现能力、查文档、查代码、调用工具、看审计。

search
当前项目有哪些可用能力？ 让 Claude Code 通过 MetaMCP 浏览能力目录。
发现
wiki
相关文档和历史方案在哪里？ 在授权 KB 内做检索或问答。
知识
codegraph
代码里哪里实现，谁调用了它？ 查询仓库、文件、符号、调用关系和影响面。
代码
profile
这个项目能不能用这些能力？ 切换或展示 Project Profile 的可见范围。
治理
logs
刚才发生了什么？ 查看调用日志、耗时、成功失败和失败归因。
审计
建议准备录屏兜底。现场实时演示优先，如果网络或模型不稳定，立刻切到录屏，不影响节奏。
Demo Script

演示台词可以这样设计

  • “我现在不是去翻文档，而是先问 Agent：这个项目有哪些可用能力？”
  • “Agent 不需要知道每个系统在哪里，它只需要连接 Agent Bridge。”
  • “它先查知识库，拿到文档证据；再查 CodeGraph，定位代码实现和调用关系。”
  • “注意这里不是所有项目都能看到所有资源，Profile 会做项目级隔离。”
  • “最后看日志：刚才的每一次能力发现、调用、失败或成功，平台都能审计。”
这个反差要让大家看到：我们不是让 Agent 更会聊天，而是让 Agent 接上了部门能力。
演示目标：让非技术同事也能看懂“统一入口”的价值。

建议讲法：先从 Claude Code 入口讲，再解释 Agent Bridge 为什么在中间。
What It Does

Agent Bridge 把松散系统变成可治理资产

Register

能力注册

登记外部 MCP 服务、Wiki 知识库、CodeGraph 仓库，形成统一目录。

Discover

能力发现

通过 MetaMCP search，让 Agent 先知道当前项目能用什么。

Govern

项目治理

通过 Project Profile 控制不同项目可见的工具、知识库和代码仓库。

Observe

调用审计

记录每次调用的结果、耗时、失败阶段和责任方，便于排障和运营。

它不是知识库本身，也不是模型本身，而是部门 Agent 能力的连接层和治理层。
这里可以回扣标题：从“人去找”变成“Agent 通过能力平面去找”。
Why It Matters

对不同角色，价值不一样

01

对个人

少翻文档、少问人、少重复配置。Agent 能直接从授权范围内找知识、查代码、调用工具。

02

对项目

能力按项目 Profile 管理，项目需要的知识库、代码仓库和工具可以组合复用。

03

对部门

把文档、代码、接口、模型和工具沉淀成可运营资产，能治理、能审计、能演进。

领导关注治理与复用，同事关注效率与少走弯路，这页两边都能接住。
Next Step

后续不是继续堆功能，而是进入能力运营

Step 1

补知识资产

把高频文档、FAQ、接口说明、项目资料整理进知识库，并明确归属。

Step 2

接代码仓库

选择试点项目进入 CodeGraph，先覆盖仓库概览、文件查询、符号定位和影响分析。

Step 3

接外部能力

把稳定的数据库查询、公共服务接口、内部 API 以 MCP 形式纳入统一目录。

Step 4

做评估运营

看哪些能力被频繁调用、哪些知识命中不好、哪些工具容易失败，再持续优化。

结尾可以邀请大家提供试点：一个知识库、一个代码仓库、一个高频工具，就能组成下一轮演示素材。
Closing

让经验不只留在人和文档里，也能成为 Agent 可以调用的部门能力

Agent Bridge 要解决的不是“多一个系统”，而是让部门已有的知识、工具、代码和模型基础设施被更稳定地发现、复用、治理和演进。

从今天开始，我们可以把“我知道在哪里”逐步变成“平台知道在哪里，Agent 能按规则使用”。
