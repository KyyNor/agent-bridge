1. 需求一 · Git 文档同步

原文：知识库除了传静态文档外，还支持传一个 Git 地址；同步程序定期拉取该地址，对特定文档（按目录过滤、按后缀过滤）传递到知识库；对于文档更新的，需要先删除再插入。

需求拆解

  • 来源扩展：知识库的文档来源从「单一人工上传」扩展为「人工上传 + Git 仓库」。
  • 周期拉取：由调度程序定期 git fetch + reset --hard，而非一次性导入。
  • 过滤规则：按目录（相对路径前缀，可多条）+ 按后缀（白名单，复用 ALLOWED_EXTENSIONS）筛选。
  • 更新语义：内容变更的文档走「先删除再插入」，确保后端不会残留旧版本（Weknora 等会以新 ID 重新解析）。
  • 删除收敛：仓库中已删除的文件，也要在知识库中删除。

2. 可复用资产盘点

资产位置如何复用
Git 拉取 + 认证 codegraph/service.py：_sync_git / _advance_branch / _auth_url / _embed_credentials / _embed_token 抽出为 knowledge/git_client.py 通用模块（或直接 import 复用），支持 username_password / token 认证嵌入，fetch --all --prune + reset --hard origin/<branch>。
连通性测试 codegraph/service.py：test_clone（git ls-remote） 配置保存时校验 Git 可达性，复刻现有 CodeRepoView 的「测试连接」交互。
仓库本地克隆目录 paths.repos_dir（repos/） Git 文档源克隆到 paths.repos_dir / "docs" / <source_slug>，与代码仓库隔离。
文档归档 + hash knowledge/archive.py：ArchiveStorage.store 返回 content_hash / file_size / archive_path 同步时对每个文件做归档，用 content_hash 判断是否变更。
同步任务队列 sync_jobs 表 + _run_job（Operation.create/update/delete） Git 源产生的增/改/删一律落到 sync_jobs，由既有 DocSyncScheduler.sync() 统一消费，无需新执行器。
APScheduler 注册 DocSyncScheduler / CodeGraphScheduler 新增 GitDocSyncScheduler（或复用 DocSyncScheduler 的同一次 doc_sync_cron 触发，在 _run_sync 中先跑 Git 源拉取）。
后端多目标 backend_targets（一个 KB 可挂多个后端） Git 文档源产出的文档天然支持多后端同步，无需特殊处理。

关键复用点：Git 文档源的输出不是「直接调后端 upload」，而是「生成 sync_jobs」。这样所有后端一致性、失败重试、KB 重建（_is_kb_gone）等既有逻辑全部自动生效，新代码只负责「Git → 本地文件 → diff → 投递任务」。

3. 数据模型

新增一张 kb_document_sources 表，描述「一个知识库从哪个 Git 仓库、按什么规则拉文档」。文档本身仍存在 documents / document_versions，但标记其来源。

-- documents 表新增列：来源标记（迁移）
ALTER TABLE documents ADD COLUMN source_slug TEXT;        -- 来自哪个 Git 源（人工上传为 NULL）
ALTER TABLE documents ADD COLUMN source_path TEXT;        -- 仓库内相对路径（用于变更比对）

为什么用 source_slug + source_path 而非重新设计文档表？

现有 documents / document_versions / document_kbs 已是成熟模型，承载版本、归档、多后端 sync_state。Git 源只是文档的「产生者」，不应破坏既有结构。新增两列做软关联：同一 source_path 的文档视为「同一个 Git 文件的化身」，用于变更/删除比对。

认证凭据存储

复用 CodeGraph 的 auth_ref JSON 约定（{type:username_password,username,password} 或 {type:token,token}）。前端列表返回时用 has_auth_ref 替换，不回传明文，与 _repository_payload 一致。

4. 同步流程（核心算法）

调度触发后，对每个 active 文档源执行以下步骤。设计目标是幂等、可重入、删后插。

1拉取仓库clone or fetch + reset --hard origin/branch，复用 _sync_git
2扫描过滤按 include_dirs + include_exts 过滤本地文件，产出候选集
3比对状态用 content_hash 与现有文档比对，分新增/更新/无变化/远端删除
4投递任务更新→delete+create job；删除→delete job；新增→create job
5记录 commit更新 last_commit / last_synced_at，交给 DocSync 消费

增量比对规则（决定 diff 的关键）

情况判断依据动作
新文件source_path 在仓库有、库中无create_document + create sync_job(create)
内容变更source_path 都有，但 content_hash ≠ 现版本 hashdelete sync_job + 新版本 + create sync_job（先删后插）
无变化hash 相同跳过
远端删除库中有此 source_path、仓库已无delete_document（生成 delete sync_job，含后端删除）

为什么「更新」也走 delete+create 而非 update job？当前 _run_job 的 update 分支只是再 upload 一次，Weknora 会生成新文档 ID而旧文档残留，造成重复入库。「先删后插」保证后端干净。这也正是需求里「先删除再插入」的本意。实现上：对同一 doc 先 enqueue delete job，再 enqueue create job（新 doc 实体），保证语义等价且可被既有执行器消费。

伪代码：GitDocSyncService.sync_source()

def sync_source(self, actor, source_slug):
    src = store.get_kb_doc_source(source_slug)
    local = paths.repos_dir / "docs" / source_slug
    # 1. 拉取
    self._sync_git(src, local)                 # 复用 codegraph 范式
    # 2. 扫描过滤
    candidates = self._scan(local, src.include_dirs, src.include_exts)
    # 3. 比对
    existing = store.list_docs_by_source(source_slug)   # {source_path: doc}
    seen = set()
    for rel_path, file_path in candidates.items():
        seen.add(rel_path)
        archived = self.archive.store(file_path)
        doc = existing.get(rel_path)
        if doc is None:
            self._create_doc_from_source(src, rel_path, archived, actor)   # + create job
        elif doc_version_hash(doc) != archived.content_hash:
            self._delete_then_insert(src, doc, rel_path, archived, actor)  # 删后插
    # 4. 远端删除收敛
    for rel_path, doc in existing.items():
        if rel_path not in seen:
            service.delete_document(actor, doc["slug"], later=True)        # delete job
    # 5. 记录
    store.mark_source_synced(source_slug, local, head_commit(local))

与现有文档同步的衔接：Git 源只产出 sync_jobs，真正上传/删除由 DocSyncScheduler.sync() 执行。因此可以在同一次 doc_sync_cron 触发里，先跑所有 Git 源拉取（产生任务），再跑 service.sync()（消费任务），形成一条流水线。

# service.py
def list_backend_agents(self, actor, slug):
    require_admin_user(actor, self.admins)
    adapter = self._get_adapter(slug)
    if not isinstance(adapter, WeknoraBackend):
        return []                 # 非 weknora 不支持 agent
    agents = adapter.list_agents()           # 原始 Weknora payload
    return [self._normalize_agent(a) for a in agents if isinstance(a, dict) and a.get("id")]

def list_backend_agent_types(self, actor, slug):
    require_admin_user(actor, self.admins)
    adapter = self._get_adapter(slug)
    if not isinstance(adapter, WeknoraBackend):
        return []
    presets = adapter.get_type_presets()
    return [self._normalize_agent_preset(p) for p in presets if isinstance(p, dict) and p.get("id")]

def create_backend_agent(self, actor, slug, name, preset_id):
    require_admin_user(actor, self.admins)
    adapter = self._get_adapter(slug)
    if not isinstance(adapter, WeknoraBackend):
        raise ValidationError(f"backend '{slug}' does not support agents")
    # 注意：create_agent(name, preset_config) 传的是整个 preset，不是 id
    preset = next((p for p in adapter.get_type_presets() if p.get("id") == preset_id), None)
    if preset is None:
        raise NotFound(f"agent type preset '{preset_id}' not found")
    return self._normalize_agent(adapter.create_agent(name, preset))

@staticmethod
def _normalize_agent(a):          # 归一化成稳定契约，不绑死 Weknora 字段
    cfg = a.get("config") or {}
    return {"agent_id": a.get("id"), "name": a.get("name") or a.get("id"),
            "agent_type": cfg.get("agent_type") or cfg.get("system_prompt_id"),
            "is_builtin": bool(a.get("is_builtin", False))}

直接选 list_agents() 返回的某个 agent（含 id）。存入 default_agent_id / retrieval_agent_id。适合已由 ensure_hybrid_agent 或人工创建好的 agent。

按「类型预设」创建 Agent

用户从 get_type_presets() 选一个类型（如 hybrid-rag-wiki），调用 create_agent 创建实例，拿到 id 后再存。适合「我要一个该类型的新 agent」。前端可在下拉里分两组：「现有 Agent」「按类型新建」。

(3) agent_id 与 backend_slug 的绑定关系

一个 agent 实例属于某个 Weknora 后端。因此 agent_id 只有在该后端被选中时才有意义。resolve_retrieval_strategy() 已有保护：当 target slug != strategy.backend_slug 时 agent_id 被忽略（ask() 中的 agent_id = strategy.agent_id if target slug 匹配 else None）。前端应在切换后端时联动清空/恢复 agent 选择，避免选了 A 后端的 agent 却用 B 后端检索。

10. 前端改动（两处选择控件）

(A) 知识库编辑页面 · 默认 Agent

KnowledgeView.vue 详情对话框现有「默认检索后端」编辑区（editingDefaultBackend / defaultBackendSlug）。在其下方并排增加「默认 Agent」选择：

  • 选择后端后，watch 拉取 listBackendAgents(backendSlug) 填充下拉。
  • 下拉含一个「无（使用后端默认问答）」选项 = 不设 agent_id。
  • 保存调用 api.updateKbDefaults(slug, { default_backend_slug, default_agent_id })。
  • 切换后端时若原 agent 属于旧后端，自动清空并提示。

(B) 能力平面 · 每 Profile Agent 覆盖

openPlaneDialog 现在只读 rule.retrieval_backend_slug。需同时读 rule.retrieval_agent_id；savePlaneProfiles 的 overrides 增加 retrieval_agent_id：

// 每行 profile：后端下拉（已有）+ agent 下拉（新增）
const profileAgentOverrides = ref<Record<string, string>>({})  // profileKey -> agentId

// 读取
for (const rule of rules) {
  profileBackendOverrides.value[rule.profile_key] = rule.retrieval_backend_slug || ''
  profileAgentOverrides.value[rule.profile_key]   = rule.retrieval_agent_id   || ''
}

// 保存
const overrides = {}
for (const pk of pendingProfileKeys.value) {
  overrides[pk] = {
    retrieval_backend_slug: profileBackendOverrides.value[pk] || null,
    retrieval_agent_id: profileAgentOverrides.value[pk] || null,   // <-- 新增
  }
}
await api.setResourceProfiles('wiki_kb', slug, keys, overrides)

交互细节

条件渲染

仅当所选后端类型为 weknora 且 listBackendAgents 非空时，agent 下拉才出现；否则隐藏并置空。

联动

后端变更 → 重新拉 agent 列表；旧 agent 不在新列表则清空。

容错

Weknora 不可达时下拉显示「Agent 服务暂不可用」，不阻塞后端保存。

12. 风险与取舍

风险点影响应对
删后插造成后端短暂「无文档」窗口检索在此窗口可能漏命中delete 与 create job 顺序入队、同批消费；Weknora 解析有延迟，UI 应展示 sync_state
大仓库首次同步慢首次 clone + 全量入库耗时长支持 later=True 异步入队；调度日志暴露进度（复用 progress_callback）
Git 凭据安全auth_ref 明文存 SQLite沿用 CodeGraph 既有约定（内部可信 VM）；列表接口仅返回 has_auth_ref；后续可接入 vault
agent 跨后端误用选 A 后端 agent 但用 B 后端检索resolve_retrieval_strategy 已忽略不匹配 agent_id；前端切换后端联动清空
Weknora 版本差异type-presets / agents 接口字段不稳list_agents 容错为空数组；前端条件渲染，不强依赖
过滤规则误配include_dirs 写错导致漏同步新增「预览命中文件」功能（test 端点返回过滤后文件列表）

总结：两个需求都建立在现有成熟架构之上。需求二风险最低（纯接线），建议先做；需求一复用 CodeGraph 的 Git 同步范式 + 既有 sync_jobs 队列，核心新增是「文档源表 + diff 编排」，不触碰后端执行层。整体可在一个迭代内交付。
