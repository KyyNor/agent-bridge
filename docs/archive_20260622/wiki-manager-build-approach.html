wiki-manager build strategy

用一层可控账本，把内网知识库从“后端绑定”变成“可迁移体系”

本项目不重新实现 RAG 引擎，而是在 RagFlow、WeKnora、未来 MaxKB 等后端之上建设统一管理面： 保存原始资料、维护逻辑知识库、记录版本和同步状态，再通过 CLI、HTTP API 和 MCP 把能力交给人和大模型。

CLI 面向普通 Linux 用户的日常维护入口
API 127.0.0.1 本机服务承载共享账本
Adapter Mock、RagFlow、WeKnora 后端可替换
MCP 给大模型暴露只读检索和问答工具
项目定位 架构分层 文档生命周期 后端适配 阶段路线

项目定位

先明确它解决的不是“怎么切片、怎么向量化”，而是“企业内部知识体系如何长期可管、可追溯、可迁移”。

CONTROL PLANE
one sentence wiki-manager 是企业知识库的胶水层、账本层和运维控制面。

所有通过本工具维护的知识，都会留下原始文件、逻辑知识库归属、版本、权限、同步任务、后端文档 ID 和状态。 即使更换后端，也可以从本地账本重放知识体系。

不替代知识库后端 RagFlow、WeKnora 继续负责解析、切片、向量化和问答。
不把业务绑死在单一系统 业务面对的是逻辑知识库和统一命令，后端可按配置增减。
不让大模型直接改资料 MCP 侧优先只读，暴露 search / ask，避免模型误修改知识资产。

架构分层

核心思路是把用户入口、服务账本、原始归档、后端适配、大模型工具拆开，每层职责单一。

LAYERS

用户与大模型入口

普通用户通过 CLI 操作；上层智能体通过 MCP 只读访问 search / ask。

wiki add / wiki sync / mcp search

本机 HTTP 服务

服务只监听 127.0.0.1，统一处理权限、上传、队列、查询和后端调用。

FastAPI + X-Wiki-User

账本与归档

SQLite 记录知识库、文档、版本、成员、任务和同步状态；archive 保存原始文件。

SQLite + immutable versions

后端注册表

从 server.toml 读取已配置后端，统一创建 Adapter 实例。

BackendRegistry

适配器协议

所有后端实现同一组 create / upload / status / retrieve / ask 方法。

BackendAdapter Protocol

真实知识库后端

Mock 用于验证闭环；RagFlow 和 WeKnora 用于真实入库、检索和问答。

mock / ragflow / weknora
1 逻辑知识库优先 工具内的 KB 是 canonical 组织单位，不等同于某个后端 dataset。
2 原始资料必须留存 迁移、重放、排查和版本回溯都依赖本地 archive。
3 同步状态可审计 每个“文档 × KB × 后端”都有独立状态和后端文档 ID。
4 检索能力受控暴露 MCP 只提供查询工具，让大模型可用但不越权。

文档生命周期

设计重点是把“上传文件”扩展为可追踪的生命周期，而不是一次性的后端调用。

LIFECYCLE
创建逻辑 KB 管理员创建知识库，并按 Linux 用户授予 viewer、contributor、admin 权限。
添加原始资料 用户通过 CLI 上传 PDF、Word、Excel、Markdown 等文件，可指定一个或多个 KB。
写入账本和归档 生成文档 slug、保存不可变版本、记录 owner、hash、文件大小和归属关系。
生成同步任务 立即同步或使用 --later 进入队列，支持夜间统一同步，避免白天抢资源。
同步到后端 按配置后端逐个上传，记录 backend_doc_id、解析状态、chunk 数和错误信息。

后端适配器思路

适配器把不同后端 API 差异挡在项目内部，让 CLI、API、MCP 不需要知道底层系统差异。

ADAPTERS 
class BackendAdapter(Protocol):
    def create_kb(slug, name) -> str: ...
    def upload(kb_id, doc_slug, file, filename) -> str: ...
    def delete(kb_id, doc_id) -> None: ...
    def get_status(kb_id, doc_id) -> BackendDocStatus: ...
    def retrieve(kb_id, question, top_k=6) -> list[RetrievalResult]: ...
    def ask(kb_id, question, chat_id=None, session_id=None) -> AskResult: ...
Mock 第一阶段用于跑通账本、权限、队列和状态机，不依赖真实后端。
RagFlow 验证真实 dataset、document 上传、解析状态、检索和 Chat Assistant 问答。
WeKnora 通过 HTTP API 完成 KB 创建、文件上传、SSE 问答和 references 映射。
Future MaxKB 或其他后端只要实现同一协议，就能接入现有账本和入口。

三个使用面

同一套服务层对外提供三种入口：人用 CLI，系统用 API，大模型用 MCP。

SURFACES
/usr/bin/wiki

CLI：给内部用户

适合部署在部门 wiki 虚拟机上，普通 Linux 用户用短命令维护资料。

  • 创建 KB、授权成员
  • 添加、更新、删除文档
  • 查看同步状态、手动 sync
127.0.0.1:8765

HTTP API：给服务编排

FastAPI 只监听本机，所有共享账本和归档操作集中在服务端执行。

  • 统一权限判断
  • 统一文件上传和版本记录
  • 统一同步任务消费
mcp://wiki-manager

MCP：给大模型

暴露只读 search 和 ask 工具，让智能体能检索知识，但不直接管理资料。

  • search：返回匹配 chunk
  • ask：返回答案和引用
  • 支持指定 KB 和 backend

阶段路线

项目按风险拆分：先验证账本闭环，再接真实后端，再开放检索和 MCP，最后扩展更多来源和后端。

ROADMAP
phase 1

入库账本闭环

先不碰真实 RAG，证明管理模型成立。

  • 逻辑知识库
  • 权限和版本
  • 归档和队列
  • Mock 后端
phase 2

真实后端同步

接入 RagFlow，验证 Adapter 和多后端同步。

  • BackendAdapter
  • 后端自动绑定
  • 状态增强
  • 迁移重放
phase 3

检索与 MCP

让知识体系从“可管理”进入“可被大模型使用”。

  • search / ask
  • 默认检索后端
  • CLI/API 查询
  • MCP 只读工具
phase 4+

WeKnora 与扩展

接入更多真实后端和更多知识来源。

  • WeKnora HTTP API
  • SSE 问答解析
  • API 文档来源
  • 多后端混合

关键设计取舍

这些取舍能解释为什么项目采用现在的结构，而不是直接让用户去操作 RagFlow 或 WeKnora。

WHY
为什么要有本地账本？

因为后端只知道自己的文档 ID 和解析状态，不负责企业内部“谁维护、属于哪个逻辑知识库、原始文件在哪、如何迁移”的完整治理。

为什么要保存原始文件？

后端迁移、重新解析、版本回退、失败排查都需要原始资料。只保存向量库结果会让知识资产被后端锁定。

为什么先做 Mock？

先把权限、版本、队列、同步状态机跑通，可以把项目风险从“业务模型不清”和“后端 API 不稳”中拆出来。

为什么 MCP 只读？

大模型适合查知识、总结知识、引用知识，但不应直接删除或修改企业知识资产。写操作仍由 CLI/API 的人类流程控制。

领导讨论口径

wiki-manager 的价值不是“多一个上传工具”，而是把内网知识从单个 RAG 后端中抽象出来： 资料有账本、版本可追溯、后端可替换、同步可审计、检索可通过 MCP 供大模型使用。
