# wiki-manager 项目定义

日期：2026-05-29

## 1. 一句话定义

`wiki-manager` 是企业内部知识库的胶水层、账本层和运维控制面。它维护经由本工具构建的知识体系，记录原始资料、逻辑知识库、用户归属、同步目标和后端状态，并在不同知识库后端之间提供统一的运维入口。

## 2. 背景

企业内部知识通常分散在不同来源和不同 RAG/知识库系统中。不同后端在文档管理、入库、检索、问答、权限、迁移能力上各不相同。如果业务直接依赖某一个后端，后续切换系统、同步多后端、追踪文档来源和恢复知识体系都会变得困难。

`wiki-manager` 的目标不是重新实现一个完整知识库后端，而是在现有后端之上增加一层可控的管理面：

- 文档从哪里来。
- 属于哪些逻辑知识库。
- 由谁维护。
- 当前同步到了哪些后端。
- 后端中的文档 ID 和状态是什么。
- 删除、更新、迁移时应该对后端执行哪些操作。

## 3. 核心职责

### 知识对接

长期支持多种知识来源接入，例如 API 文档、URL、代码仓库、数据库说明、传统办公文档等。不同来源可以被转换成统一格式的 Markdown 或归档为原始文档，再进入知识库体系。

第一阶段暂不实现 API 文档生成和 Markdown 转换，优先支持传统文档的归档和入库管理。

### 知识维护

提供添加、更新、删除、计划入库等维护能力。用户可以将文档加入逻辑知识库，也可以选择计划模式，让文档先进入队列，夜间统一同步到后端，避免白天抢占模型和解析资源。

### 后端无关运维层

对上提供统一的知识库运维语义，对下适配不同后端，例如 RagFlow、WeKnora、MaxKB。用户不需要在日常操作中关心不同后端的 API 差异。

长期能力包括：

- 查询知识库列表。
- 检索知识库内容。
- 向知识库问答。
- 查看文档同步状态。
- 对多个后端执行同步或迁移。

第一阶段只做入库账本和 mock 后端同步，不做检索和问答。

### 同步与迁移

所有通过本工具入库的知识都保留本地记录和原始存档。这样在切换后端时，可以根据本地账本重放原有知识体系，尽量做到无缝迁移。

删除也属于同步的一部分：用户在本工具中删除文档后，本工具应记录删除意图，并将后端中的对应文档同步移除。

### 大模型服务层

长期提供简易 MCP 服务，让大模型能够通过受控工具访问知识库检索能力。MCP 服务应优先只读，避免大模型意外修改知识库内容。

第一阶段不实现 MCP，等基础入库账本和后端适配稳定后再加入。

## 4. 非目标

`wiki-manager` 不承担以下职责：

- 不替代 RagFlow、WeKnora、MaxKB 等知识库后端。
- 不直接负责复杂文档解析、切片、向量化和 RAG 推理。
- 不把所有外部来源都强制转换为同一种内部内容格式。
- 不在第一阶段实现完整权限安全边界。
- 不在第一阶段提供 Web UI。

它的核心价值是管理、归档、编排和适配，而不是重新造一个知识库引擎。

## 5. 逻辑知识库模型

本工具维护自己的逻辑知识库。逻辑知识库不等同于某个后端里的知识库，而是本工具中的 canonical 组织单位。

例如：

```text
frontend-docs
  -> 同步到 mock
  -> 未来可同步到 RagFlow
  -> 未来可同步到 MaxKB
```

同一个原始文档可以属于多个逻辑知识库。每个“文档 × 知识库 × 后端目标”都有独立同步状态。这样可以支持多个小组共享同一份材料，也可以支持同一知识体系同步到多个后端。

## 6. 多用户部署模型

目标部署环境是部门内部 wiki 虚拟机。root 安装 CLI 和本机服务，普通 Linux 用户使用 CLI 操作。

第一阶段采用本机 HTTP 服务：

```text
普通用户
  -> wiki CLI
  -> 127.0.0.1 HTTP API
  -> wiki-manager-server
  -> /root/wiki-manager 下的配置、数据、归档和日志
```

默认根目录：

```text
/root/wiki-manager/
  config/
  data/
  logs/
  run/
```

普通用户不直接读写共享 SQLite 和归档目录。CLI 获取当前 Linux 用户名并传给服务，服务按用户名和知识库权限过滤结果。第一阶段该模型定位为内部可信 VM，不防本机用户伪造 HTTP 请求中的用户名。

## 7. 阶段拆分

### 第一阶段：入库账本闭环

目标是验证工具自身的核心管理模型：

- 逻辑知识库。
- 用户和 KB 权限。
- 原始文档归档。
- 文档版本历史。
- 文档归属多个 KB。
- 立即入库和计划入库。
- mock 后端同步。
- 软删除和硬清理。
- CLI + 本机 HTTP 服务。

第一阶段不做真实后端、不做查询、不做 MCP、不做 Web UI。

### 第二阶段：真实后端和查询能力

在第一阶段账本稳定后，接入一个真实知识库后端，并提供基础查询能力：

- RagFlow、WeKnora、MaxKB 中选择一个优先适配。
- 实现知识库列表、文档状态、基础检索。
- 增加只读 MCP 服务。
- 验证后端迁移和重放流程。

### 第三阶段：多来源和多后端混合

扩展知识来源和运行模式：

- API 文档采集与 Markdown 生成。
- URL、代码仓库、数据库说明等来源。
- 多后端并行同步。
- 多后端混合检索。
- 更强身份认证。
- Web 管理界面。

## 8. 成功标准

第一阶段完成后，应能在部门 wiki 虚拟机上完成以下流程：

1. root 初始化 `/root/wiki-manager`。
2. 启动本机 `wiki-manager-server`。
3. 管理员创建逻辑知识库。
4. 管理员给 Linux 用户分配 KB 权限。
5. 普通用户通过 CLI 添加 PDF、Word、Excel 等传统文档。
6. 工具保存原始文件和版本记录。
7. 用户选择立即同步或计划同步。
8. 夜间通过 `wiki sync` 消费计划任务。
9. mock 后端记录每份文档的同步状态。
10. 用户更新文档时保留历史版本。
11. 用户删除文档时生成后端删除同步任务。
12. 管理员可查看全局队列和失败任务。

如果这条链路跑通，说明 `wiki-manager` 的账本模型、权限模型、队列模型和适配器边界基本成立，可以进入真实后端适配阶段。
