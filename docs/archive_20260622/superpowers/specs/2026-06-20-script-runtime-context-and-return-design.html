Design Spec

脚本运行时上下文与返回协议改造设计

本设计用于统一 Agent Bridge 脚本的执行协议、上下文透传和 workflow 顶级工具调用方式。 目标是让脚本结果不再依赖 stdout JSON，而是通过 main(envelope) -> dict 返回； 同时让 profile 和 workflow context 成为不可伪造的源请求上下文，并在脚本内自动继承。

目标一 脚本结果改为读取返回值，不再把 stdout 当结果通道。
目标二 profile 与 workflow headers 从源请求透传到脚本运行环境。
目标三 在 helper 中暴露 workflow 顶级工具，保持和 MCP 顶级工具语义一致。

1. 范围与结论

本次改造采用 硬切换：脚本必须定义 main(envelope) -> dict。 旧的 “stdout 输出 JSON 结果” 协议不保留兼容层。
  • 脚本运行结果只读取 main() 的返回值，stdout/stderr 仅作为日志采集。
  • agent_bridge_runtime.execute() 不再允许显式传 profile_key。
  • 测试运行接口需要支持注入自定义 profile/workflow headers，用于模拟真实上下文。
  • 脚本运行环境需要同时携带 profile 与 workflow context。
  • workflow_get_task / workflow_set_task / workflow_run_log 作为 helper 独立暴露，不下沉到普通 execute 子工具。

2. 当前问题

结果通道脆弱

当前脚本结果依赖 stdout 整体可被解析成 JSON object。任何普通 print() 日志都可能污染结果，导致执行失败。

上下文不完整

当前脚本只继承 profile_key，没有继承 workflow 开关、workflow_key、workflow_run_id，导致脚本无法安全调用 workflow 顶级工具。

profile 可被覆盖

当前 helper 允许显式传 profile_key，会破坏“脚本调用上下文必须与源请求一致”的约束。

workflow 工具语义错位

workflow_* 现在是 MCP 顶级工具，不属于普通 capability execute 通道。若直接把 workflow 上下文降级为普通参数，会引入伪造上下文风险。

3. 设计决策

硬切换新协议 上下文只读 workflow helper 独立暴露 测试运行支持 header

3.1 返回协议

  • 脚本文件必须定义顶级函数 main(envelope: dict) -> dict。
  • 运行器通过导入脚本模块并调用 main() 获取结果。
  • 若缺失 main、main 不可调用、返回值不是 dict，本次脚本运行直接失败。

3.2 上下文可信来源

  • profile 与 workflow context 都只能来自源请求 header。
  • 脚本作者不能通过 helper 参数覆盖这些上下文。
  • 服务端在进入脚本运行前完成 header 读取、校验、注入。

3.3 workflow 调用方式

  • 保留 workflow 工具的“顶级工具”身份，不改造成 execute(service, tool_name) 的子工具。
  • 在运行时 helper 中暴露同名函数，让脚本以 Python API 方式调用。
  • helper 内部自动透传 workflow 上下文，并由服务端复用现有 workflow run context 校验逻辑。

4. 新脚本协议

4.1 脚本入口

from agent_bridge_runtime import execute, workflow_get_task, workflow_set_task, workflow_run_log

def main(envelope: dict) -> dict:
    return {
        "ok": True,
        "script_key": envelope["script_key"],
        "params": envelope["script_params"],
    }

4.2 envelope 结构

{
  "run_id": "script_run_xxx",
  "run_type": "test | mcp",
  "script_key": "system.example",
  "script_params": {},
  "profile_key": "profile-a" | null,
  "workflow": {
    "enabled": true | false,
    "workflow_key": "page-report" | null,
    "run_id": "run_123" | null
  }
}

4.3 日志语义

  • stdout 与 stderr 继续完整采集并持久化，用于调试和审计。
  • print() 不再污染脚本返回结果。
  • 脚本返回结果与日志彻底分离。

4.4 失败条件

场景 行为
脚本没有定义 main 失败，错误信息明确为缺少 main 入口
main 返回非 dict 失败，错误信息明确为返回值类型错误
helper 调用 workflow 工具但缺少上下文 失败，错误信息明确为 workflow context is required
profile / workflow run 不匹配 失败，复用现有服务层校验错误

5. 上下文透传

5.1 源请求输入

运行脚本时，服务端需要从源请求读取以下 header：

X-Agent-Bridge-MetaMCP-Profile
X-Agent-Bridge-Workflow
X-Agent-Bridge-Workflow-Key
X-Agent-Bridge-Workflow-Run-Id

5.2 注入到脚本环境

服务端在启动脚本进程前，除了当前已有的运行参数外，还需要注入以下环境变量：

AGENT_BRIDGE_API_BASE=http://127.0.0.1:<port>
AGENT_BRIDGE_USER=<actor>
AGENT_BRIDGE_PROFILE=<profile-key or empty>
AGENT_BRIDGE_WORKFLOW=true|false
AGENT_BRIDGE_WORKFLOW_KEY=<workflow-key or empty>
AGENT_BRIDGE_WORKFLOW_RUN_ID=<workflow-run-id or empty>
PYTHONIOENCODING=utf-8

5.3 测试运行行为

  • 测试接口不再只依赖 body 里的 profile_key。
  • 测试请求也可以通过自定义 header 注入 profile 与 workflow 上下文。
  • 这样前端和人工调试都能模拟“带 workflow 上下文运行脚本”的真实路径。

6. Runtime Helper

6.1 对外 API

from agent_bridge_runtime import (
    execute,
    workflow_get_task,
    workflow_set_task,
    workflow_run_log,
)
Helper 用途 是否允许脚本传上下文
execute(service, tool_name, params=None) 调用普通 capability 不允许，profile 只能继承源请求
workflow_get_task() 获取当前 workflow run 的 pending task 不允许，workflow context 自动继承
workflow_set_task(tasks) 创建或刷新当前 workflow 的 pending tasks 不允许
workflow_run_log(...) 向当前 workflow run 追加业务日志 不允许

6.2 行为原则

  • execute() 只负责普通 capability 调用，不暴露 profile_key 形参。
  • workflow_* helper 只暴露业务参数，不暴露 workflow_key、run_id、profile_key。
  • 若当前环境没有完整 workflow context，workflow_* helper 立即失败，不返回软错误对象。

7. 服务端改造

7.1 脚本运行器

  • 从“把脚本当纯文件进程执行，然后解析 stdout JSON”切换为“加载脚本模块并调用 main(envelope)”。
  • 仍保留 stdout/stderr 采集与截断逻辑，用于日志记录。
  • 脚本运行记录中的 result_json 改为保存 main() 的返回值。

7.2 workflow runtime 接口

为了让 helper 能安全复用现有服务层，而不把 workflow 顶级工具错误地下沉为普通 capability，新增一组内部 runtime HTTP 接口：

POST /runtime/workflow/get-task
POST /runtime/workflow/set-task
POST /runtime/workflow/run-log
  • 这些接口只从 header 读取 trusted context。
  • 请求体只承载业务参数，例如 tasks、message、payload。
  • 接口内部直接复用现有 WorkflowService 的校验与执行逻辑。

7.3 与现有 MCP 顶级工具的关系

MCP 顶级工具定义保持不变。新增的 runtime HTTP 接口只作为脚本 helper 的内部调用入口， 不是为了改变外部 MCP 对外协议。

8. 测试与验收

8.1 需要新增或调整的测试

  • 脚本定义 main(envelope) 并返回 dict 时成功。
  • 缺少 main 时报错。
  • main 返回非 dict 时报错。
  • 脚本普通 print() 不影响结果解析。
  • execute() 始终继承源 profile，不能被脚本覆盖。
  • 脚本调用其他 MCP / OpenAPI 时继续按源 profile 校验。
  • 测试运行接口支持 profile/workflow headers 注入。
  • workflow_* 在无 workflow context 时失败。
  • workflow_* 在 context 完整且匹配时成功。
  • workflow_* 在 workflow/profile/run mismatch 时失败。

8.2 验收标准

验收项 标准
脚本结果协议 只认 main 返回值，stdout 不再是结果通道
profile 继承 脚本内所有普通 capability 调用均沿用源 profile
workflow 继承 脚本内 workflow helper 只能使用源 workflow context
测试运行 可通过 header 模拟 profile 与 workflow 运行环境

9. 风险与非目标

9.1 风险

  • 硬切换会让所有旧脚本立即失效，因此需要同步更新已有脚本模板和内置示例。
  • 脚本运行器从子进程 stdout 解析切到模块调用后，需要仔细处理异常、导入隔离与日志采集。
  • 新增 runtime workflow 接口时，要明确它们仅供本地运行时 helper 使用，避免和公开 API 语义混淆。

9.2 非目标

  • 本次不保留旧的 stdout JSON 兼容模式。
  • 本次不把 workflow 顶级工具改造成普通 capability execute 子工具。
  • 本次不扩展脚本语言支持范围，仍只支持 Python 脚本。
