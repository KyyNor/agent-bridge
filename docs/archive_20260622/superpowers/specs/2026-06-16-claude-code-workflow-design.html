Agent Bridge / Workflow Knowledge Accumulation

Claude Code 动态工作流知识沉淀设计

本设计定义 Agent Bridge 如何保存和调度 Claude Code 动态工作流，并通过受控 MCP 工具提供任务领取、任务回填、运行日志和产出物检索能力。工作流内部逻辑由 Claude Code workflow JavaScript 负责，Agent Bridge 负责生命周期、权限、状态和产出物接管。

日期：2026-06-16 状态：设计规格 范围：后端 + MCP + 调度 + 控制台展示 不含：拖拽式可视化编排

目标与非目标

第一版聚焦把“反复查询一次页面知识”的过程变成可调度、可续跑、可沉淀、可检索的批处理工作流。

Scope

目标

  • 允许管理员创建 workflow，粘贴 Claude Code 动态工作流 JavaScript，并强制绑定一个 profile_key。
  • 页面根据 workflow manifest 展示节点、流转关系、输入输出结构和最近运行情况。
  • 使用统一调度器在每日开始时间和停止时间之间循环执行 workflow。
  • 通过 MCP 为 workflow agent 提供任务领取、任务回填和运行日志能力。
  • 单独管理产出物，不与现有 KB 绑定，支持 tags、path、标题、摘要和全文检索。
  • 向普通 profile agent 暴露产出物检索工具 artifacts_search。

非目标

  • 不在第一版实现拖拽式工作流编辑器。
  • 不让 Agent Bridge 解析或执行 workflow 内部业务步骤。
  • 不把产出物自动同步到现有知识库系统。
  • 不实现复杂 DAG 调度；实际分支、循环和子 agent 编排由 Claude Code workflow JavaScript 管理。
  • 不在第一版提供人工审核流；产出物只按协议校验后入库。

职责边界

这条边界是本功能最重要的设计约束：Agent Bridge 管平台态，Claude Code workflow 管业务探索。

Boundary
职责 Agent Bridge Claude Code Workflow
定义保存 保存 workflow 名称、绑定 profile、调度配置、manifest、JS 源码。 JS 源码表达真实流程、节点含义、任务发现方式和最终输出格式。
权限 按请求头和 profile 控制 MCP 工具可见性。 通过注入的 MCP 配置调用允许的工具。
任务状态 存储 pending/running/completed/failed/abandoned 及租约。 调用 workflow_get_task、workflow_set_task 和 workflow_run_log。
调度 按全局并发与公平队列启动 claude -p。 一次启动处理一个任务，或返回没有可执行任务。
产出 校验 out/result.json，保存 artifact，完成 task。 生成标准化 result.json 和 Markdown 文件。

数据模型

模型保持平台态清晰，同时让 workflow JavaScript 自己决定任务 payload 的业务结构。

Storage

workflow_definitions

  • workflow_key：唯一键。
  • name、description、status。
  • profile_key：必填，关联 project profile。
  • workflow_js：Claude Code workflow JavaScript。
  • manifest_json：节点、边、schema、展示信息。
  • schedule_json：开始时间、结束时间、启用状态。
  • created_by、created_at、updated_at。

workflow_tasks

  • workflow_key、task_key：联合唯一，用于幂等 upsert。
  • status：pending、running、completed、failed、abandoned。
  • payload_json：由 workflow 定义。
  • lease_run_id、lease_expires_at：避免并发重复领取。
  • attempt_count、last_error。
  • created_at、updated_at、completed_at。

workflow_runs

  • run_id：每次 claude -p 启动生成。
  • workflow_key、profile_key、task_key。
  • status：running、completed、no_task、failed、stopped。
  • temp_dir、exit_code、stdout_path、stderr_path。
  • started_at、finished_at、duration_ms。

workflow_artifacts

  • artifact_id、workflow_key、run_id、task_key。
  • title、path、tags_json、summary。
  • format：第一版支持 markdown。
  • content、content_hash。
  • metadata_json、created_at。

任务写入必须幂等。workflow_set_task 对同一个 workflow_key + task_key 只更新仍未完成的任务，不覆盖 completed 任务，避免任务发现重复导致产出物反复生成。

MCP 工具与可见性

工具按请求头区分普通 agent 和 workflow agent。普通 agent 只看到产出物检索；workflow agent 额外看到任务与日志工具。

MCP
工具 可见对象 行为 返回
artifacts_search 普通 profile agent、workflow agent 按 profile 可见范围、query、tags、path、workflow_key 检索产出物。 artifact 清单，包含标题、路径、标签、摘要、片段和详情读取所需标识。
workflow_get_task workflow agent 返回一个可执行 pending task，并原子设置为 running 与租约。 有任务时返回 task；无任务时返回 { "task": null }。
workflow_set_task workflow agent 批量 upsert pending task，任务状态均为未完成。 写入数量、跳过数量、已存在数量。
workflow_run_log workflow agent 追加运行日志，包含 stage、level、message、payload。 { "ok": true }。不参与业务判断。

MCP 可见性由 HTTP 请求头决定。推荐使用 X-Agent-Bridge-MetaMCP-Profile 指定 profile，并新增 X-Agent-Bridge-Workflow: true 与 X-Agent-Bridge-Workflow-Key 标记 workflow agent 身份。

调度模型

所有 workflow 共用一个调度器，采用公平队列与小批次运行，避免大 workflow 长时间占满队列。

Scheduler
每日窗口开始 | v 加载 active workflow -> 标记今日可运行 | v while 当前时间 < stop_time: 找到可用并发槽位，最多 2 个 workflow run 按 round-robin 选择不同 workflow 为每个 workflow 启动一次 claude -p run 结束后解析 out/result.json - completed: 保存产出物，完成 task - no_executable_task: 标记该 workflow 今日结束 - failed: 记录失败，释放或重试 task 继续填充空槽位，不等待整轮全部完成 | v 到 stop_time 或所有 workflow 今日结束 -> 停止启动新 run

并发

全局同时最多 2 个不同 workflow run。第一版不允许同一个 workflow 同时运行多个 run，以降低重复领取任务和输出冲突风险。

公平

调度器维护 workflow 轮转游标。某个 workflow 完成一次 run 后排到队尾，空槽位出现时立即补位，不等待上一组全部完成。

结束

workflow 返回 no_executable_task 后，当日不再调度；到达 stop time 后不再启动新 run，正在运行的 run 可按配置优雅等待或终止。

用户示例中的 A/B/C/D 会自然交错：A 第一次返回无任务后当日结束，B/C/D 按空槽位轮转领取任务，直到所有 workflow 无任务或到达停止时间。

Claude Code 启动方式

Agent Bridge 只负责启动 Claude Code，并提供运行目录、MCP 配置、workflow 源码和固定提示词。

Runtime
  1. 调度器创建随机临时目录，例如 <data>/workflow-runs/<run_id>。
  2. 写入 workflow.js、prompt.md、.mcp.json 和输出目录 out/。
  3. .mcp.json 指向 Agent Bridge MCP endpoint，并注入 profile 与 workflow 请求头。
  4. 使用 claude -p 运行固定 prompt，要求执行当前目录的 workflow 并最终写入 out/result.json。
  5. 捕获 stdout/stderr、退出码、耗时和 debug 信息。
  6. 进程结束后由 Agent Bridge 校验 result，并更新 run、task、artifact 状态。
claude -p \
  --mcp-config ./.mcp.json \
  --append-system-prompt-file ./workflow-system-prompt.md \
  "Run the workflow defined in ./workflow.js and write the final result to ./out/result.json."

第一版不依赖 Claude Code 交互式确认。workflow 运行所需 MCP 工具必须通过 profile 和请求头预先暴露；如果 Claude Code 因权限或配置失败退出，Agent Bridge 只记录失败并按任务策略释放或标记失败。

产出物协议

产出物由 workflow 生成，Agent Bridge 只认标准化结果文件。第一版主格式为 Markdown。

Artifacts

完成任务

{
  "status": "completed",
  "task_key": "page:finance/report-a",
  "artifacts": [
    {
      "title": "报表 A 页面知识报告",
      "path": "reports/finance/report-a/index.md",
      "tags": ["report", "finance", "etl"],
      "format": "markdown",
      "file": "out/artifacts/report.md",
      "summary": "页面使用表、加工逻辑、访问人群和数据来源汇总",
      "metadata": {
        "page_key": "finance/report-a"
      }
    }
  ]
}

无任务可执行

{
  "status": "no_executable_task",
  "reason": "task discovery finished and no pending task remains"
}
  • completed 必须包含当前 task_key，并至少包含一个 artifact。
  • file 必须位于本次临时目录内，禁止读取临时目录外路径。
  • path 用于页面树形组织和检索过滤，不代表本地文件路径。
  • 同一 workflow_key + path 默认保留最新版本，同时记录历史版本可作为后续增强。
  • 解析失败、文件缺失、格式不支持会使 run 失败，task 不会标记 completed。

控制台页面

页面展示流程信息，而不是实现拖拽编辑器。工作流作者通过 manifest 让平台稳定渲染节点和数据结构。

Frontend

创建/编辑 Workflow

  • 基础信息：key、name、description、status。
  • 必选关联 profile。
  • 粘贴 Claude Code workflow JavaScript。
  • 从源码顶部或单独输入框保存 manifest JSON。
  • 配置每日开始时间、停止时间和是否启用。
  • 校验 manifest 必须包含 nodes、edges、schemas。

查看 Workflow

  • 节点清单：id、name、description、inputs、outputs。
  • 流转关系：edge 起点和终点。
  • 数据结构：task、artifact、关键中间结构。
  • 运行状态：今日是否结束、当前 run、最近失败、任务统计。
  • 产出物树：按 path 分层展示，支持 tags 和全文搜索。
  • 日志：按 run 和 task 查看 workflow_run_log。
export const manifest = {
  name: "页面知识沉淀",
  nodes: [
    { id: "get_task", name: "领取任务", outputs: ["task"] },
    { id: "discover_tasks", name: "发现任务", outputs: ["tasks"] },
    { id: "analyze_page", name: "分析页面", inputs: ["task"], outputs: ["report"] },
    { id: "emit_artifact", name: "输出产物", inputs: ["report"], outputs: ["artifact"] }
  ],
  edges: [
    ["get_task", "analyze_page"],
    ["get_task", "discover_tasks"],
    ["discover_tasks", "get_task"],
    ["analyze_page", "emit_artifact"]
  ],
  schemas: {
    task: { task_key: "string", payload: "object" },
    artifact: { title: "string", path: "string", tags: "string[]" }
  }
};

失败处理与租约

任务领取必须具备原子租约，否则两个 Claude 进程可能处理同一个 task。

Reliability
  • workflow_get_task 使用数据库事务选取最早 pending task，并立即写入 running、lease_run_id、lease_expires_at。
  • 默认租约 2 小时。租约过期的 running task 可被下一次领取前回收为 pending，并增加 attempt_count。
  • run 正常完成且 result 为 completed 后，Agent Bridge 将 task 标记为 completed。
  • run 失败、result 缺失或 artifact 校验失败时，task 标记为 failed 或释放为 pending，具体取决于 attempt_count 是否超过阈值。
  • workflow 返回 no_executable_task 只结束该 workflow 当日运行，不删除历史任务和产出物。
  • 到达 stop time 后不再启动新 run。正在运行的 run 第一版默认允许完成；后续可增加强制终止策略。

测试策略

第一版要重点验证权限隔离、调度公平性和产出物接管协议。

Verification

存储与服务测试

  • 创建 workflow 必须绑定存在的 profile。
  • task upsert 幂等，不覆盖 completed。
  • task lease 原子领取，租约过期可回收。
  • artifact path/tags/query 可检索。

MCP 测试

  • 普通 profile 只能看到 artifacts_search。
  • workflow header 下可看到四个工具。
  • workflow agent 不能访问非本 workflow 的任务工具。
  • artifacts_search 只返回 profile 可见产出物。

调度测试

  • A/B/C/D 示例按 round-robin 交错执行。
  • 全局并发不超过 2。
  • no_executable_task 使 workflow 当日结束。
  • stop time 后不再启动新 run。

实施顺序

为了降低风险，先把平台态和协议跑通，再逐步补齐 UI 和真实 Claude 调度。

Plan Seed
  1. 新增 workflow 存储 schema、repository、service 和 API。
  2. 实现 MCP 工具可见性和四个工具。
  3. 实现产出物保存与检索服务。
  4. 实现调度器核心，不直接依赖真实 Claude，先用 fake runner 测公平性。
  5. 接入真实 claude -p runner，完成临时目录、MCP 配置和结果接管。
  6. 实现控制台 Workflow 页面和 Artifacts 页面。
  7. 补充端到端 smoke test：一个 fake workflow 发现任务、处理任务、生成 Markdown。
