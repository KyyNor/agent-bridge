Agent Capability Hub / Phase 1.5

能力治理与调试闭环设计

Phase 1 已经完成 MCP 服务登记、工具同步和 MetaMCP search/execute。 Phase 1.5 不进入操作类工具治理，而是补齐调用日志、能力目录、详情页面、Project Profile、 服务级白名单/黑名单、Profile 强制裁剪和 Claude Code 接入 CLI，让平台从“可登记可调用”升级为“可治理、可追踪、可接入项目”。

1. 阶段边界

本阶段优先做治理闭环。操作类工具治理、审批、dry-run 和工具级策略不进入 Phase 1.5。

Scope

本阶段要做

  • 新增 tool_call_logs，记录 MetaMCP 和原始工具调用日志。
  • MetaMCP search / execute 返回 log_id。
  • 新增能力目录、能力详情、完整工具详情页。
  • 新增 Project Profile 和服务级白名单/黑名单。
  • Profile 请求头过滤和服务端强制裁剪。
  • 新增 Claude Code 接入 CLI。
  • 现有管理页面全部中文化，风格继续对齐 docs/design/。

本阶段不做

  • 不开放 action 工具执行。
  • 不做审批流、二次确认和 dry-run。
  • 不做工具级 allow/deny。
  • 不引入 React、Vite 或复杂前端构建链。
  • 不把日志默认脱敏；完整记录是本阶段内部可信环境策略。
  • 不重命名既有 mcp_services / mcp_tools 表。

2. 架构分层

治理能力必须落在服务端，不依赖页面隐藏或 CLI 约束。页面和 CLI 只负责管理与接入，策略执行在服务层和 MetaMCP 网关层完成。

Architecture

治理数据层

新增工具调用日志、Project Profile 和 profile source rules。命名避免绑定 MCP，后续 OpenAPI、CLI、脚本 runner 能复用同一套治理表。

治理服务层

新增治理服务或在能力服务中拆出治理子模块，统一负责 profile 解析、服务可见性判断、执行校验和日志写入。

MetaMCP 网关层

读取 profile 请求头，对 search 和 execute 强制过滤与校验。所有调用都返回或关联 log_id。

管理控制台与 CLI

控制台中文化并扩展能力目录、日志、Profile 和接入配置页面。CLI 负责写入 Claude Code 配置和调用 profile 管理 API。

3. 数据模型

新表使用通用能力命名。当前 source 类型主要是 MCP 服务，后续可以接入 OpenAPI 或 CLI 工具。

Data
表 用途 核心字段
tool_call_logs 记录所有工具调用日志，不绑定 MCP。 log_id, actor, profile_key, entrypoint, source_type, source_key, tool_name, request_json, response_json, status, error_message, duration_ms, created_at
project_profiles Project Profile 主表。 profile_key, name, description, status, created_by, created_at, updated_at
profile_source_rules Profile 服务级访问规则。 profile_key, source_type, source_key, effect, created_at
当前 source_type 使用 mcp_service。后续接入 OpenAPI、CLI 或脚本 runner 时，只扩展 source 类型，不换治理表。 既有 mcp_services 和 mcp_tools 仍作为 MCP 资产表保留。

4. Profile 策略规则

本阶段只做服务级白名单/黑名单。工具级策略留到实际使用数据和日志沉淀后再扩展。

Policy

规则语义

  • 没有 profile：默认可见所有 enabled source。
  • 有 deny：排除 deny 中的 source。
  • 有 allow：只允许 allow 中的 source。
  • allow 和 deny 同时存在：先按 allow 缩小范围，再应用 deny。
  • 未知 profile：报错并写调用日志。

服务端强制

  • search 必须过滤候选服务和工具。
  • execute 必须再次校验目标 service。
  • 被阻断的 execute 不调用目标 MCP。
  • 页面和 CLI 不能作为唯一策略执行点。
{
  "profile_key": "safe-readonly",
  "rules": [
    {"source_type": "mcp_service", "source_key": "mysql", "effect": "allow"},
    {"source_type": "mcp_service", "source_key": "hive", "effect": "deny"}
  ]
}

5. 服务端接口

接口分为 Project Profile、Tool Call Logs 和能力目录三组，供页面和 CLI 共用。

API
接口 用途 说明
POST /capability-profiles 创建或更新 profile。 字段包括 profile_key、name、description、status。
GET /capability-profiles 列出 profiles。 返回规则数量、allow/deny 摘要和最近更新时间。
GET /capability-profiles/{profile_key} 查看 profile 详情。 返回 profile 基本信息和 rules。
PUT /capability-profiles/{profile_key}/rules 全量替换规则。 规则字段为 source_type、source_key、effect。
GET /tool-call-logs 调用日志列表。 支持按 entrypoint、source_key、tool_name、profile_key、status 筛选。
GET /tool-call-logs/{log_id} 调用日志详情。 返回完整 request/response JSON、错误信息和耗时。
GET /capability-catalog 能力目录。 支持 profile_key 预览和 query 搜索。
GET /capability-catalog/sources/{source_type}/{source_key} 能力来源详情。 当前主要返回 MCP 服务、工具数量、同步状态和最近调用情况。
GET /capability-catalog/sources/{source_type}/{source_key}/tools/{tool_name} 工具详情。 返回 schema、示例、可执行状态和最近调用日志。

6. MetaMCP 调用链

MetaMCP 是治理强制执行的关键入口。search 和 execute 都必须写日志，并返回或关联 log_id。

Gateway

Search

1
解析请求头读取 X-Wiki-MetaMCP-Profile。
2
构造策略上下文加载 allow/deny source rules。
3
过滤候选能力按 profile 裁剪服务和工具。
4
执行 path/query完成目录浏览或过滤。
5
写日志并返回返回 path/items/log_id。

Execute

1
解析 profile读取请求头或默认策略。
2
校验 source阻止被 deny 或未 allow 的服务。
3
校验工具必须 active 且非 action。
4
调用目标工具执行 HTTP MCP call_tool。
5
写日志并返回返回 service/tool/success/result/log_id。

8. Claude Code 接入 CLI

CLI 负责管理 profile 和写入 Claude Code MCP 配置；策略判断仍由服务端执行。

CLI 
 wiki metamcp profile create safe-readonly --name "安全只读"
 wiki metamcp profile rules safe-readonly --allow mysql --deny hive
 wiki metamcp profile list
 wiki metamcp profile show safe-readonly

 wiki metamcp add --scope project --url http://127.0.0.1:8765/mcp --profile safe-readonly
 wiki metamcp add --scope user --url http://127.0.0.1:8765/mcp --profile data-project
 wiki metamcp config --scope project

CLI 写入内容

  • MetaMCP 服务 URL。
  • X-Wiki-MetaMCP-Profile 请求头。
  • 项目级或用户级 scope。
  • 当前有效配置摘要。

配置安全边界

  • CLI 生成配置，但不承担服务端策略判断。
  • 服务端必须对 profile 做最终强制裁剪。
  • 测试使用临时目录验证配置写入，不污染真实 Claude Code 配置。

9. 错误处理与日志策略

日志按完整记录设计。后续企业化时可以打开脱敏和截断策略，不改变表结构。

Errors
场景 处理方式 日志状态
Profile 不存在 返回 profile not found，不继续调用。 error
服务被 profile 阻止 search 隐藏；execute 拒绝，且不调用目标工具。 blocked
service/tool 不存在 沿用 NotFound 语义，记录请求参数。 error
action 工具执行 继续拒绝，作为策略阻断处理。 blocked
目标 MCP 调用失败 记录完整 request 和错误结构 response，返回错误和 log_id。 error
调用成功 记录完整 request/response、耗时和 profile。 success
Phase 1.5 默认 redaction_mode=none。设计预留 max_payload_bytes、 request_truncated 和 response_truncated，用于后续限制超大 payload 或开启字段级脱敏。

10. 测试与验收

测试重点是服务端强制裁剪、日志闭环、中文页面和 CLI 配置写入。

Acceptance

测试分层

  • Storage：日志、profile、rules CRUD。
  • Policy：无 profile、allow、deny、allow+deny、未知 profile。
  • CapabilityService / MetaMCP：search/execute 过滤、阻断、log_id。
  • API：profile、日志、能力目录和详情接口。
  • CLI：profile 管理和 Claude Code 配置写入。
  • 页面：中文文案、静态资源、导航入口。

验收流程

  • 登记 mysql、hive 两个 MCP 服务。
  • 创建 profile safe-readonly，deny hive。
  • 携带 profile 调用 search {}，只看到 mysql。
  • 直接 execute service=hive 被服务端拒绝。
  • 日志页面能看到 search 日志和 execute blocked 日志。
  • CLI 能生成 Claude Code 接入配置并绑定 profile。
  • 控制台主要文案全部中文，视觉不偏离设计稿。
