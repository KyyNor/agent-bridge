先给结论

Understand Anything 已经直接提供多平台安装入口，但它本质上是 skill 文件投影、宿主工具调用和 Subagent 编排，不是一个对四种后端做统一抽象的运行时。 Agent Bridge 当前也还没有做到四个后端的能力对齐：Claude 最完整，OpenCode 有托管 MCP 路径，Codex 和 Pi 的 MCP、skill、Subagent 支持存在明显空白；工具输入/输出和 Token 也没有统一的运行级数据模型。下面的路线图以“用户可见契约一致，后端内部实现可不同”为目标。

01

审查结论：多平台安装 ≠ 后端能力对齐

这里把上游项目和当前 Agent Bridge 的事实分开。能力矩阵中的“支持”只表示当前代码路径已经接入； “部分”表示只能依赖 prompt、工作区配置或 best-effort 解析，不能当成稳定的公共契约。

1深度原生 skill / Subagent 集成：Claude
2当前可走 Agent Bridge MCP 路径：Claude、OpenCode
0统一的运行级 Token 字段

Understand Anything 上游

上游 README 和 install.sh 已列出 Codex、OpenCode、Pi 等平台。 安装方式主要是把同一个 skill 投影到宿主约定的目录；技能正文会调度 project-scanner、file-analyzer、assemble-reviewer、tour-builder、graph-reviewer 等多个 Subagent。

因此答案是“支持其他宿主”，但不是“所有宿主已经拥有统一的 Agent Bridge 运行时能力”。 上游插件本身也没有为这些平台提供一个 MCP 服务来抹平差异。

当前运行时

AgentService 已统一运行目录、请求装配、结构化结果提取、运行级耗时、 费用、轮次、messages.jsonl、events.jsonl 和持久化入口。 这提供了很好的骨架，但不同 adapter 对请求字段和原始事件的消费仍不一致。

通用事件可以识别工具调用和工具结果，但没有统一保留工具 input/output； 原始 JSONL 是否含这些字段取决于后端输出。

最重要的缺口

当前 supports_cost 表示“能得到费用”，不等于能得到 input/output/total token；duration_ms 主要是整次 run 的墙钟耗时， 不是每个工具调用的耗时。

Claude 有专门的 Subagent transcript 解析；其他三个 adapter 当前没有等价的 Subagent 生命周期和层级信息。

02

目标：用户看到的是同一套信息流

“几个后端能力大致相同”不要求每个后端都采用同一种原生协议，而要求同一个场景在 UI、 API 和持久化层拥有可比较的行为。后端做不到的字段也必须显式说明原因。

  1. 统一用户侧契约。 相同的请求能力（skill、MCP、结构化结果、Subagent、停止）都应在发起前通过 capability negotiation 得到明确结果；不支持时拒绝、降级并记录，不允许静默忽略。
  2. 原始信息和规范信息同时保留。 adapter 负责把后端事件映射为 canonical event，同时保存可追溯的 raw message；规范化失败不能丢失原文。
  3. 大 payload 延迟读取。 列表和时间线只加载摘要、大小、类型和 preview；几十 KB 到几百 KB 的输入输出通过二次请求/抽屉加载，避免一次运行拖垮页面和 API。
  4. Subagent 是一等实体。 Subagent 应有自己的生命周期、工具事件、耗时、费用和 Token，并通过 parent-child 关系挂回主 run；不能只在一段字符串里显示。
  5. 统计口径先于展示。 明确主 agent、Subagent、重试和并行任务的 Token/费用是否聚合，避免前端将父子数据重复相加。
  6. 安全边界内可观测。 原始输入输出可能包含密钥、源码、个人数据；存储前要做可配置脱敏，并同时记录“已脱敏 / 未获取 / 获取失败 / 不支持”状态。
03

统一信息模型：Run、Event、Payload、Subagent

现有的 agent_runs、messages.jsonl、events.jsonl 和 MCP 的 tool_call_logs 可以作为兼容基础，但需要建立稳定的 ID 和引用关系。 大内容不宜直接塞进事件行或列表 API。

Backend raw message保留后端原始 JSONL / SDK 事件
Adapter normalize转换为 canonical event，记录能力与降级
Payload store短内容 inline，长内容 artifact + 引用
API / UI时间线摘要，二次加载详情和 Subagent 树

RunSummary agent_runs

  • run_key、backend、model、session_id、状态和结束原因
  • started_at、finished_at、duration_ms，继续使用 monotonic 计算持续时间
  • usage：input、output、cache、reasoning、total tokens；每个值带 source/status
  • cost：金额、币种、来源和是否为估算值
  • root_subagent_id、事件总数、工具调用总数、payload 总字节数

CanonicalEvent events.jsonl / DB

  • event_id、run_key、递增 seq、时间戳和 kind
  • actor_type：main_agent / subagent / tool / system；actor_id 和 parent 引用
  • status：started、streaming、succeeded、failed、cancelled、unknown
  • 工具事件包含 tool_call_id、工具名、provider、duration_ms
  • 事件只带 summary 和 payload reference，不强制内联完整内容

PayloadRef artifact

  • side：input / output / error / transcript；content_type 和编码
  • bytes、sha256、是否截断、是否脱敏、保存期限
  • preview 仅保存受限长度；artifact_uri 指向文件或对象存储
  • 详情读取必须走鉴权、范围限制和分页/下载策略

SubagentNode tree

  • subagent_id、parent_subagent_id、parent_tool_call_id
  • agent name、backend、model、prompt summary/ref、生命周期和终止原因
  • 自己的事件、工具、usage、cost、duration 和结果引用
  • 支持并行子任务；聚合统计通过明确的 aggregation_mode 防重复计算

字段状态不能再靠 null 猜测

对 Token、工具 output、Subagent 或 partial message 等信息，建议采用 { value, status, source, reason } 的统一形状，至少区分： available not_emitted not_collected unsupported。 这样用户可以分辨“后端没有提供”和“系统本来应该采集但采集失败”。

默认时间线

  • 每个工具调用展示名称、开始/结束状态、耗时、输入/输出大小和摘要。
  • 短 payload 直接显示受限 preview；行内不加载几十 KB 以上的全文。
  • 失败显示错误阶段、错误类型和可追踪的 raw event ID。
  • 未收到结束事件时标记为 interrupted 或 unknown，不伪造 succeeded。

详情抽屉

  • 用户点击“查看输入/输出”后，前端按 payload_ref 读取详情。
  • 详情页支持语法高亮、搜索、复制、下载、换行切换和分页/范围读取。
  • 超大内容不在列表 API 中返回；后端可设置最大在线预览大小。
  • 内容不可用时说明是未采集、过期、脱敏还是后端未提供。

推荐阈值（待定案）

  • ≤ 8 KiB：事件中内联 preview，可直接展示。
  • 8 KiB–64 KiB：保存 artifact，事件只返回摘要和短 preview。
  • 64 KiB–1 MiB：二次加载，支持分段读取或下载。
  • ＞ 1 MiB：默认不在线全文渲染，仅提供统计、搜索索引或下载。

阈值是产品初始建议，不是实现承诺；应通过真实运行样本和前端性能测试校准。

05

存储与 API：摘要快路径，详情慢路径

运行列表、状态轮询和时间线首屏需要稳定、轻量；payload 和原始 transcript 是可按需取回的详情资源。 这也让后续从本地文件迁移到对象存储时不必改变 UI 契约。

资源职责首屏是否返回全文建议的关键字段兼容策略
agent_runs 运行级摘要和最终结果 否 run、backend、model、status、duration、usage、cost、root subagent 保留已有字段；新增 JSON/nullable 字段，旧 API 继续可用
agent_run_events 规范化事件时间线 按页 event_id、seq、kind、actor、parent、status、summary、payload refs 可由现有 events.jsonl 回填；messages.jsonl 保留作为 raw source
agent_payloads 工具输入/输出、错误、transcript 详情 二次读取 payload_id、content_type、bytes、preview、artifact、sha256、redaction 先用 run 目录文件，抽象 URI；未来再换对象存储
subagent_nodes 父子任务树和子任务摘要 树 + 按需详情 subagent_id、parent、agent、model、lifecycle、usage、cost、result ref Claude 专用详情可先映射；没有协议时明确 unsupported

四个后端的落地重点

适配器仍然是差异隔离边界。应用层只消费 capability registry 和 canonical event， 不应重新增加按后端类型分支。

后端优先补齐可以直接复用需要谨慎处理目标
Claude tool input/output、tool duration、Token 分项、原生 abort、Subagent 完整树 SDK partial message、MCP、skill、schema、现有 Subagent transcript 解析 SDK 对象序列化；父子 usage 聚合和 Task transcript 版本差异 作为 canonical event 的第一套完整参考实现
Codex MCP 配置投影、skill/AGENTS 投影、tool payload 解析、Token/耗时、Subagent 事件 JSONL 进程管理、native JSON schema、abort、result/cost/turn 解析框架 确认 CLI 当前 JSON 事件协议；不能把 prompt 注入冒充 native skill 将当前“结果可用”提升为“过程可观测”
OpenCode skill 投影、native schema 或稳定结果协议、tool payload、Token/turn、Subagent 托管 opencode.json MCP 配置、JSONL、abort、run duration MCP 配置格式和 CLI 事件版本；当前 turns capability 为 false 从“可运行 MCP”补齐完整事件和资源引用
Pi MCP、skill 投影、tool payload、Token 分项、Subagent、事件结束状态 JSON mode、partial text、abort、费用聚合和 assistant turn 计数 Pi 是否暴露足够的原生扩展/事件；必要时提供兼容层并标注来源 从“输出流适配”提升为完整运行时适配

Capability contract

扩展现有 CodingAgentCapabilities，将能力拆成 request_mapping、event_stream、payload_capture、 usage、subagents 等维度，并携带版本、来源和降级模式。

显式降级

例如后端没有 token breakdown，应返回 usage.input_tokens.status = not_emitted，同时仍记录 run duration 和 raw message；不让前端把空值误认为 0。

适配器测试夹具

每个后端固定保存成功、工具失败、超时/中止、长 payload、Subagent、缺少 usage 的 JSONL fixture；同一 fixture 断言 canonical event，而不是只断言最终文本。

08

验收标准：相同场景可比较、可追溯

“已支持”需要由可观测的验收条件定义。不能只看最终回答是否出来，因为这会掩盖工具失败、 Subagent 丢失和 Token/耗时统计不完整等问题。

  • 同一测试场景在 Claude、Codex、OpenCode、Pi 上都能返回同一 canonical event 形状；后端差异落在 adapter。
  • 每个工具事件都有稳定 call ID、工具名、开始/结束状态、成功/失败原因和耗时；缺少结束事件必须可识别。
  • 工具 input 和 output 都有摘要、大小、类型和 payload ref；短内容可直出，长内容点击后加载，不默认返回全文。
  • 详情读取支持权限校验、脱敏标识、内容不可用原因，以及范围读取/下载，不能因为大输出导致运行详情页崩溃。
  • Run 级和 Subagent 级都有 duration；Token 和 cost 按统一口径记录，无法取得时有明确 status/reason。
  • Subagent 能以树显示 parent、生命周期、自己的工具和统计；主任务与子任务聚合可切换且不会重复计数。
  • skill、MCP、schema、abort、partial 等 request 能力在发起前可查询；未支持能力不得静默丢弃。
  • raw message 永久/按策略保存并能通过 event ID 回溯；canonical 解析失败时仍能诊断原始后端事件。
  • 运行期间 events 和 payload 元数据持续落盘；进程异常、中止、超时后仍能看到最后一个可靠状态。
  • 四个后端都有 parser fixture 和至少一条真实 managed-run E2E；测试覆盖成功、失败、长输出、并行和 Subagent。
09

开始实现前需要定下的事项

原始内容保存多久？

需要决定默认保留期、单个 payload 和单次 run 的总大小、是否允许用户关闭 raw 保存， 以及文件存储切换对象存储时的迁移方式。

脱敏发生在哪里？

建议在持久化前做可配置脱敏，同时保留脱敏计数和规则版本；如果只在前端脱敏， 数据库和下载接口仍可能泄露原始值。

Token 和费用怎样聚合？

明确 provider 返回的是估算还是实际值，父子任务是否包含关系，重试是否单独计入， 以及“当前不可得”与“数值为 0”的区别。

能力缺失如何处理？

对原生不支持 MCP、skill 或 Subagent 的后端，是做 bridge-managed 兼容层， 还是只提供显式 unsupported。产品选择会影响 adapter、权限和测试范围。
