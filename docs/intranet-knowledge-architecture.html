MCP 与大模型知识库：平级能力，还是知识库统一汇总？

当前分歧不是“是否建设大模型知识库”，而是结构化知识是否应被降级为文档后再进入知识库。 对数据血缘、SQL 逻辑、公共服务接口这类可查询、可约束、可执行的知识，MCP 更像能力接口； 对制度、手册、历史资料等非结构化文档，大模型知识库更适合作为语义检索入口。

结构化知识 数据加工链路、SQL、接口文档、报表查询路径、服务依赖关系。
非结构化知识 制度文档、操作手册、Word、Excel、PDF、历史说明材料。
上层应用 Claude Code、网页问答、智能体、运维查询、开发辅助。
关键议题 “要访问哪些服务”和“接口怎么调用”是否能被同一个 example 字段完整承载。

MCP 能力层 查询检索、参数化访问、实时结果、example、调用约束

模式 B：所有信息进入大模型知识库汇总

重点：这个模式的入口更简单，但会把“可查询能力”变成“文档快照”。关系、参数、实时状态、服务选择逻辑和接口调用约束都可能在切片与召回中被削弱。

核心差异

维度 模式 A：MCP + 大模型知识库平级 模式 B：知识库统一汇总
本质定位 MCP 是结构化知识的能力接口；知识库是非结构化资料的语义检索入口。 知识库成为唯一汇总入口；MCP 更像生成文档快照的中间工具。
准确性 结构化问题可以按参数查询，返回精确对象、字段、关系和来源。 依赖文档切片和召回，复杂关系容易被拆散，答案更偏摘要。
实时性 MCP 可以直接读取当前数据源或当前服务目录，更新链路短。 需要导出、入库、切片、索引刷新，存在文档快照滞后。
表达能力 能表达“查询条件、接口参数、依赖关系、可调用动作、example”。 更擅长表达“文字说明、制度解释、操作步骤、历史背景”。
用户体验 上层应用需要一个编排层判断调用 MCP 还是 RAG，但答案可更精确。 入口统一，建设初期更容易解释，但上层应用拿到的多是文本答案。
治理方式 对 MCP 做接口契约、权限、审计、版本和字段级治理；对知识库做文档治理。 治理集中在知识库，但结构化数据的版本、权限和溯源需要额外补救。
主要风险 需要建设统一路由和权限策略，避免上层应用直接散连多个 MCP。 结构化能力被扁平化为文档，复杂场景下可能“看似有知识，实际不可执行”。
适用场景 开发辅助、服务接入、血缘追踪、SQL 解释、报表定位、故障排查。 制度问答、手册查询、跨文档摘要、培训材料、低频参考资料。

公共服务接口 example 的边界问题

领导设想中的边界

  • 接口文档：放在知识库中被检索。
  • example：只描述“怎么使用接口”，包含说明和代码样例。
  • 上层应用：从知识库召回文档，再生成调用建议。

实际项目中的边界

  • 先要判断访问哪些服务：这是服务发现、场景匹配、依赖关系问题。
  • 再判断接口如何调用：这是接口契约、参数、鉴权、返回结构问题。
  • 最后生成调用样例：这才是 example 应该承载的核心内容。
业务意图 新项目要查询客户、交易、权限或报表数据
服务发现 应访问哪些公共服务，为什么需要，依赖什么前置条件
接口使用 endpoint、参数、鉴权、返回结构、代码 example
如果“要访问哪些服务”只隐含在 example 里，知识会变得不可治理：RAG 可能只召回某个接口的调用样例，却漏掉服务选择依据、替代服务、前置依赖和项目适配规则。
服务目录 记录服务能力、适用场景、业务域、数据范围、替代关系。
服务选择规则 回答“当前项目需要访问哪些服务”，并给出选择理由。
接口契约 回答“接口怎么调”，包含参数、鉴权、响应、错误码和限制。
调用 example 沉淀“在某场景下如何调用”，包含文档说明和代码样例。

建议把 example 定位为“接口调用样例”，但不要让它独自承载服务发现。服务发现与接口契约应在 MCP 中保持结构化字段，也可以同步导出为知识库文档快照供普通问答使用。

建议口径

建议采用“统一入口，双源供给”的折中架构。 大模型知识库负责承接制度、手册、PDF、Word、Excel 等文档型知识；MCP 负责承接结构化、实时、可参数化、可执行的知识能力。 上层应用看到的是一个统一知识入口，但入口背后按问题类型路由到 MCP 或知识库。

可以向领导确认的共识

  • 用户入口可以统一，不需要让用户理解 MCP 和知识库的差别。
  • 文档型知识进入大模型知识库是合理的，也是必要的。
  • MCP 也可以定期导出摘要文档，供知识库做背景检索和引用。

需要保留的底线

  • 不要把 MCP 仅定义为“导出 md / Word 的工具”。
  • 服务发现、血缘、SQL、接口契约应保留结构化查询入口。
  • example 不能替代“要访问哪些服务”的服务选择知识。
讨论时可以这样表述：知识库负责“读懂文档”，MCP 负责“查准结构和执行约束”。如果把 MCP 的能力全部文档化，短期入口更统一，长期会损失实时性、精确性和可执行性。
